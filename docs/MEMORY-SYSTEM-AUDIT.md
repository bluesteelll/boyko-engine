# Memory System Audit (2026-07)

**STATUS: findings under fix (goal track 1).** Four parallel structured readers inventoried every
durable buffer in the engine (66 buffers across the VM core, kernel side-structures, boyko_utils
primitives and their use sites, and cross-crate subsystem storage). Verdict semantics:
**MISPLACED** = scales with entities/rows on a hot path and is NOT on the kernel VM backing;
**QUESTIONABLE** = defensible but improvable; **OK-by-design** = fixed/type-scaled/transient-reused/FFI.

## Executive summary

The kernel hot-storage contract HOLDS where it matters: component bytes + both tick columns share
one address-stable `VmReservation` per pool; dense component VALUES live in a real `ComponentPool`;
entities live in the VM `InlandStore`; the rigid-solver chain is verifiably on kernel
`ScratchColumn`. The engine is archetype-based - `SparseMap` is bookkeeping, NOT the component store.

Two real holes (both per-entity/per-row scaled, hot, non-VM) + two adjacent under-provisions:

| # | Finding | Fix |
|---|---------|-----|
| F1 | `Archetype.entity_ids` (row->entity) is a plain `Vec<EntityId>` - the ONLY per-row hot column not on VM; realloc-doubling on batch spawns reintroduces the X.G memcpy-spike class | new kernel `VmColumn<T>` primitive (InlandStore-shaped reserve/commit-frontier), swap in |
| F2 | `DenseStore.e2s` entity->slot map is a generic `SparseMap` (16 B/max-id sparse layer + a redundant sparse->dense double hop) probed PER ROW on the mixed dense query path | flat sentinel `Vec<u32>` (slot-or-MAX): 28->4 B/entry at 1M entities, 1 load per probe; dedupe the double `slot_of` |
| F3 | `DenseStore.s2e` (slot->entity) is a realloc-able Vec whose raw pointer a hot iterator caches | move onto `VmColumn<EntityId>` (address-stable, commit-in-place) |
| F4 | `DENSE_STORE_RESERVE_ROWS = 1024` is a hard ceiling with a PANIC on exhaust - an under-reserve for the designated "one buffer for ALL instances" storage | raise to `pool_reserve_rows(stride)`-class (VA is free); make bookkeeping growth lazy accordingly |
| F5 | `SoftColorScratch` CSR is std-Vec, sound only via an implicit built-then-frozen invariant (one refactor from an SP4 recurrence) | pin the freeze invariant with debug asserts (ScratchColumn move deferred to the soft-body dense migration) |

Deliberate KEEPs (documented, re-affirmed): `free_entity_ids` (structural-only), observer
`by_entity` (sticky-bit gated, tiny counts), clone/prefab O(max-id) transient maps (cold; the
sorted-Vec swap is recorded if spikes are ever measured), `Children` element Vecs (v1 collection
contract reserves the dense backing swap), SoftBody per-particle Vec columns (constructor-frozen;
migration target = DENSE-COMPONENTS-PLAN), demo snapshot mirrors (already-filed dogfooding port).

Recommendations (vm_core):

- **Archetype.entity_ids (row->entity swap-remove bookkeeping)** [MISPLACED]: move to the VM class (an InlandStore-shaped EntityId column per archetype, or a ComponentPool-backed column): it is the only per-row hot column NOT on VmReservation — Vec doubling reintroduces the exact realloc-memcpy spike class X.G deleted for entities_inland, on every batch spawn
- **DenseStore.column (dense component data)** [QUESTIONABLE]: placement is correct (VM), but DENSE_STORE_RESERVE_ROWS = 1024 (dense_registry.rs:33) is a HARD immutable ceiling — ComponentPool::new uses it exactly (component_pool.rs:249, bypasses the POOL_MIN/MAX clamp) and insert PANICS past it (dense_store.rs:156 'reserve ceiling exhausted'). Dense is the designated 'one buffer for ALL instances' storage; 1024 is an UNDER-reserve. Raise to pool_reserve_rows(stride)-class (VA is free)
- **DenseStore bookkeeping (e2s SparseMap<u32> / s2e Vec<EntityId> / live LiveBitmap / free Vec<u32>)** [QUESTIONABLE]: defensible (granted exception, preallocated to the ceiling so no realloc until the ceiling is raised); if the 1024 ceiling grows to millions, the eager with_capacity becomes ~17 MB committed heap per store — switch bookkeeping to lazy-commit VM then
- **EntityMaster.free_entity_ids (id recycle LIFO)** [QUESTIONABLE]: keep — entity-scaled but touched only on create/delete paths that already pay the cache line (doc at :70-72); a mass-despawn burst can still realloc-spike; a fixed prealloc or VM slab is a cheap belt if profiles ever show it

Notes: VM reservations per world: N = 1 (InlandStore, lazy 1 GiB) + SUM over archetypes of |Table components| (one VmReservation per ComponentPool) + |materialized DenseStores| + |ScratchColumns|. Default small-stride pool reserves 1 GiB data + 2x64 MiB ticks VA; ZST tag pool 128 MiB VA (2 tick regions at 2^24 rows, constants.rs:125-128). constants.rs:41-45 budgets 3000 pools ~3.4 TiB = 2.7% of 128 TB VA, <=6 VMAs/pool vs vm.max_map_count 65530. Windows 64 KiB granule waste (RESIDENT, the real cost): commit floor per non-empty pool = 3 granules = 192 KiB (data+added+changed each round to 64 KiB; constants.rs:87-89 states it) — a 1-row archetype with C components holds C x 192 KiB; ZST pool floor 128 KiB; InlandStore first slab 256 KiB. Example: 100 sparse archetypes x 3 components ~ 56 MiB resident floor. VA rounding waste <= 64 KiB/reservation; stagger pad (<4032 B) shares granule 0, no extra granule. Over-reserved BY DESIGN: yes and deliberate — 1 GiB/pool, 1 GiB inland, 128 MiB/tag-pool are PROT_NONE address space with zero commit charge. The one inversion: DenseStore's 1024-row HARD ceiling (under-reserve, panics at dense_store.rs:156). Headline findings: (1) Archetype.entity_ids is the sole per-row hot Vec left off VM — MISPLACED; (2) dense ceiling 1024; rest of the VM story checks out line-for-line (write-once bases, in-place frontier commit, zero-fill tick contract, ScratchColumn genuinely pool-backed).

Recommendations (kernel_side):

- **DenseStore.e2s (entity->slot map)** [MISPLACED]: sentinel-pack: flat Vec<u32> (slot directly, u32::MAX tombstone) kills the redundant sparse->dense hop (1 load, 4x denser); DenseRegistry itself rejects SparseMap for exactly this reason (dense_registry.rs:37-45); optionally VM-back it. Note: the Dense plan explicitly granted this Vec (dense_store.rs:48-49), so it is documented-deliberate but not layout-deliberate
- **DenseStore.s2e (slot->entity back-map)** [QUESTIONABLE]: co-locate as a third sub-region of the column's VmReservation (exactly like the tick sub-regions) — removes the only realloc-able buffer a hot iterator caches a raw pointer into, and rides the same commit-in-place growth
- **EntityObserverStore (by_entity + arena + free_list)** [QUESTIONABLE]: cold, so acceptable; but observing one high-id entity allocates 16 B x id of sparse — sentinel-pack the handle map (Vec<u32>, u32::MAX = absent) for 4x density, or measure first (observer counts are tiny in practice)
- **RelationshipTarget reverse index (Children(Vec<Entity>))** [QUESTIONABLE]: v1-deliberate: collection.rs:4-7 explicitly reserves a dense/arena backing as a future type swap behind RelationshipSourceCollection with zero hook changes; keep until a traversal-heavy workload measures the heap hop

Notes: Verified against source, graphify-oriented. Cross-cutting: (1) The kernel contract holds where it matters — component bytes and BOTH tick arrays share one address-stable VmReservation ([data|added|changed], component_pool.rs:135); dense values live in a real ComponentPool; Exclusive and FK relations are fully in-column. (2) The single hottest non-VM per-entity structure is DenseStore.e2s: the generic SparseMap costs 16 B/max-entity-id plus a redundant sparse->dense double hop, and it is hit per row per frame by every MIXED dense query (data.rs:677 + :717 — twice per row: passes + fetch). Sentinel-packed flat Vec<u32> is a 1-load, 4x-denser drop-in; dense_registry.rs:37-45 already documents this exact critique of SparseMap. (3) Pointer-caching discipline is consistently borrow-scoped: DenseSolveView (column base + live words), DenseQueryIter (s2e ptr), Enable/IsEnabled fetches (*const EnableColumn re-read per set_table_*) — all invalidation windows require &mut, so no dangling class exists; only the pool VM base and event buffers are cached long-term, and both never move. (4) s2e (Vec<EntityId>, 8 B/row, per-frame, raw-ptr-cached in the iterator) is the one buffer that would benefit from riding the column reservation as a third sub-region like ticks. (5) EnableTag bits are heap 512 B pages, not VM, but the layout is equally deliberate (cache-line pages, lazy alloc cap, summary word skip, O(1) toggle without migration) — the price of togglability without archetype moves. (6) EntityObserverStore's sparse map scales with MAX observed entity id (16 B/id) — cold and 0%-gated, but a foot-gun for a single high-id observed entity. (7) No archetype-edge cache exists anywhere; the OnceLock bundle table (fixed 1024) is the only spawn-path cache, world-owned and size-pinned.
