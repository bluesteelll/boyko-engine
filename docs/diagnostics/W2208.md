# boyko-W2208 - mesh geometry could not be allocated in device-local memory

## What happened

`build_mesh_gpu` asked for a `MemoryLocation::DeviceLocal` buffer for a mesh's vertices or
indices, the allocation failed, and the mesh was created in host-visible memory instead:

```text
boyko-W2208: mesh geometry: no device-local allocation for 10260288 bytes - the buffer stays
host-visible, so every draw fetches it across the bus (MEASURED ~40x slower on the shadow depth
passes of a discrete GPU)
```

Raised from `crates/boyko_render/src/mesh_assets.rs`. The mesh is fully usable: it registers,
uploads and draws exactly as it would have, and the frame is correct. Only its SPEED changes.

## Why

This is a `Warn` and not an `info!` because the consequence is a measurement, not a preference.

Until 2026-08-26 every mesh in this engine was allocated host-visible unconditionally, and nothing
said so. On a discrete GPU that means system RAM: the vertex fetch crosses PCIe on every draw, and a
mesh is drawn many times per frame - once into the G-buffer, once per shadow cascade, once per
punctual cube face. A 24-vertex cube never showed it. One 160 k-vertex model (10.3 MB) did:

| GPU zone (median, RTX 3060 Laptop) | host-visible | device-local |
|---|---|---|
| `ZONE_GBUF_PUNCTUAL_DEPTH` | 4.247 ms | 0.121 ms |
| `ZONE_GBUF_CSM_DEPTH` | 1.797 ms | 0.067 ms |

The cost tracked BYTES x PASSES, not triangles - the signature of a bus read rather than of
rasterisation. That is the regression this code exists to name, because a reader who does not know
where the geometry lives will look for it in the shadow code, in the material, in the model - and
find nothing wrong there.

`RatePolicy::Once`: whether a device-local heap can be served is a property of the device, so the
second mesh reports nothing the first did not.

## How to fix

- **Out of video memory.** The usual cause on a real GPU, which does have a device-local heap. Check
  what else is resident: another application holding VRAM, or this scene registering more (or
  larger) meshes than the card has room for. A 160 k-vertex model costs ~10 MB of vertex buffer at
  the engine's 64-byte vertex; a corpus of them adds up.
- **A device with no device-local heap the allocator can serve.** Rare, and legitimate - a software
  rasteriser (`BOYKO_FORCE_SOFTWARE`, lavapipe) has no dedicated memory to give. Nothing is wrong;
  the warning is telling you the frame times you are about to measure are not comparable to a
  hardware run.
- **Nothing to do.** The fallback is deliberate: a device that cannot place geometry in VRAM should
  still run the scene, slower, rather than refuse to boot. If the warning fires on hardware you
  expect to have VRAM, treat it as the memory-pressure report above rather than as a rendering bug.
