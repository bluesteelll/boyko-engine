# boyko-E2103 — a mandatory target or descriptor ring failed to build

## What happened

One of the VB split's own mandatory rings could not be built while the split was armed, so the
builder drained whatever it had already created and yielded `None`:

```text
boyko-E2103: vb_geo_aux_set build failed under an armed VB split (OOM-class) -- record_vb will
             refuse the frame
```

Four sites raise it, all in `crates/boyko_rhi_vulkan/src/present/targets.rs`, and the `{}` names
which: `thin_normal ring allocation`, `vb_geo_aux_set`, `vb_ssao_set`, `vb_split_set1`. They run at
target build and at every resize — never per frame.

`RatePolicy::Every`, and that is about call frequency rather than severity: a `Once` would report
the first resize that ran out of device memory and stay silent through every one after it, which is
exactly when a reader most needs to see it repeat.

## Why

**The next thing that happens is a panic, and without this line its message is the wrong story.**
`record_vb` consumes all four of these with `.expect(..)`
(`present/passes/vb.rs:3706`, `:3776`, `:4291`, and `thin_normal` through the two match arms that
require it), so a `None` here becomes an `invariant: a split-armed boot builds …` panic on the next
frame. That text says an invariant was violated; the actual event was that the device refused an
allocation one resize earlier, in a different function. This code is what connects them.

It is an `error!` and not a `warn!`, and the split from [`boyko-W2106`](W2106.md) is a measurement
rather than a matter of taste. Seven sites in that file degrade to `None`; `record_vb` consumes
**four** with `.expect(..)` and **three** with `if let Some(..)`. One group kills the frame, the
other loses an opt-in effect and renders. In this registry the class letter *is* the level, so one
code could not have carried both without telling an operator that losing a shadow denoise and
losing the frame are the same event.

## How to fix

Every one of the four is OOM-class — a descriptor pool or a device allocation that could not be
served — so the fix is to reduce demand or increase supply:

- **Lower the render resolution or the window size.** These rings are per-frame-in-flight and scale
  with the extent; a resize that fails at 4K commonly succeeds at 1440p.
- **Close what else is holding VRAM.** Another engine instance, a browser with hardware
  acceleration, a video encoder. `thin_normal` in particular is a full-extent image ring.
- **Turn the split off.** `mesh_geo_shade_split` is a render-path choice, not a requirement; the
  deferred path builds none of these rings. If the device cannot afford the split, running without
  it is a legitimate configuration and not a workaround.

**If the allocation should have succeeded**, this is a report worth escalating rather than
working around: the four subjects are small relative to the G-buffer that was already built by the
time they run, so a failure here on a device with headroom points at descriptor-pool sizing rather
than at VRAM.
