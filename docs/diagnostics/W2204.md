# boyko-W2204 - lights with a non-finite position or range were dropped from the GPU light table

## What happened

The light fold rejected one or more point/spot lights whose position had a non-finite component, or
whose range was NaN:

```text
boyko-W2204: dropped 3 point/spot light(s) with a non-finite position (or a NaN range) from the GPU
light table; a NaN centre would otherwise be culled INTO every froxel
```

Raised from `crates/boyko_render/src/light_system.rs`. The dropped rows are not written and are not
counted in the header's `point_spot_count`; every finite light closes up behind them, so the table
stays dense and the frame renders normally without them.

## Why

The clustered cull tests each light's sphere against every froxel. A NaN centre does not fail those
tests - it makes them meaningless, and the standard failure is that the light is culled *into*
every froxel in the view, at which point one bad light costs the shading pass the entire light
list. Rejecting the row on the host, once, before it is ever written, is far cheaper than defending
against it per froxel per frame.

**The count is the point of this code.** Its predecessor called a `#[cold]` reporter once per
dropped light behind a one-shot latch, so the single record that survived always described exactly
one drop - the number was structurally always `1`. The tally now accumulates in the fold and is
reported once at the end, which costs one `u32` increment on a branch that was already being taken
and one compare per fold call.

**This is a different code from `boyko-W2201`**, which reports lights dropped because the table was
full. Same class, same level, same one-line consequence - and different fixes: "your scene has too
many lights" is not "one of your lights has a NaN". A registry code is a documented condition with
one explanation and one repair, so two repairs mean two codes.

`RatePolicy::Once`, per site: the fold runs every frame and a scene with a NaN light has it on every
one of them.

## How to fix

Find the light, not the renderer - the value arrives from gameplay data:

- **A divide-by-zero in a gameplay curve or an un-initialised `Transform`** is the usual source.
  `light_reconcile` derives a punctual light's `position` from its `GlobalTransform` when one is
  present, so a NaN in the transform hierarchy propagates here.
- **A NaN `range`** is more often authoring: a range computed from an intensity falloff divides by
  something that reached zero.
- **Do not "fix" it by clamping in the shader.** The host gate exists precisely so the value never
  reaches a consumer that cannot defend itself, and a clamp downstream would hide the source.
- **The engine deliberately does not panic here.** This is live, per-frame, gameplay-authored data;
  killing the process on a transient glitch is not a policy this path takes anywhere else.
