# boyko-W2207 - VB-SV0 was requested on a boot whose resolved render path cannot carry it

## What happened

`LightingConfig::vb_sdf_mesh_shadow` and/or `LightingConfig::vb_sdf_mesh_ao` were set, but the
render path this process resolved at boot cannot carry the VB-SV0 term, so both gate bits were
forced OFF for the run:

```text
boyko-W2207: VB-SV0 was requested (shadow=true, ao=false) on a boot whose resolved render path
cannot carry it (needs path == VisibilityBuffer, a mesh leg, ShadowSources::SDF_SOFT_MARCH,
RG8-UNORM storage, and -- since DP6a -- the geo/shade split, whose geometry half is the term's
only producer) -- both gate bits forced OFF for this run. NOTE: the split is resolved from a BOOT
SNAPSHOT of this same request, so a request first raised AFTER boot is clamped for the process
lifetime
```

Raised from `sync_sv0_light_gate` in `crates/boyko_render/src/light.rs`, once per process. The
owner's own `vb_sdf_mesh_shadow` / `vb_sdf_mesh_ao` fields are never written - the gate publishes
`request && capability` into the separate `*_armed` fields, which is what
`LightingConfig::shadow_gate_word` packs. Rendering continues; the frame is simply the unarmed one.

## Why

The report is keyed on **request vs capability**, not on the value the gate wrote. An honoured
request also moves the value, and reporting that as a clamp would cry wolf on every armed boot.

It exists because a silently-cleared request produces a frame that is **byte-identical** to the
unarmed one. The failure and its symptom are the same image, so without this line the only reading
available downstream is "the SV0 term moved zero pixels" - which is equally consistent with "SV0 is
broken" and with "this scene was never a VB x Both boot in the first place". Naming the clamp is
what separates those two.

Two things about the mechanism are worth knowing:

- **`Once`, and the latch is a named `static`.** `W2207_SITE` is module-level rather than tucked
  inside the reporter, because a `Once` latch is process state: an observer has to be able to
  `reset()` it, or a test's green only means that nothing else in the binary tripped the condition
  first. Several sibling tests in `light.rs` drive the gate over unarmable pairs, and they do trip
  it.
- **It used to be an unconditional `eprintln!`** with a hand-rolled `AtomicBool`, and the L8c print
  census reddened on it. The argument in its place - that it cannot be driven at frame rate, so it
  needs no build-profile gate - is about RATE, and rate is what `RatePolicy::Once` is for. It was
  never a reason to bypass the logger, which is what cost the record its level, its target, its
  code and its sink.

## How to fix

**If you wanted SV0 on**, the five boot preconditions are all of the message's parenthetical, and
all of them are read from the resolution, not from the request:

- `RenderPathConfig::path == RenderPath::VisibilityBuffer`
- a **mesh** geometry leg in `GeometryLegs`
- `ShadowSources::SDF_SOFT_MARCH` among the shadow sources
- RG8-UNORM storage-image support on the device
- the **geo/shade split** armed - since DP6a its geometry half is the term's only producer

`ResolvedRenderPath::vb_sdf_mesh_armable()` is the single predicate over those; read it if you want
to branch rather than be clamped.

**Set the request before boot.** The parenthetical's NOTE is the part that catches people: the
geo/shade split is resolved from a **boot snapshot of this same request**, so raising
`vb_sdf_mesh_shadow` after `app.run()` cannot arm the split that would have carried it. A request
first raised after boot is clamped for the process lifetime even on hardware and a path that would
otherwise have served it. Set the `LightingConfig` fields during app construction.

**If you are reading a log from someone else's session**, this line tells you their run had SV0 off
regardless of what their config says - which matters before comparing their screenshots or timings
against a run that had it on.
