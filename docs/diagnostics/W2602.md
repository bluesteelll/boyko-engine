# boyko-W2602 - a zlib stream's Adler-32 does not match, and the decoded pixels were kept

## What happened

A PNG's compressed pixel data inflated successfully, but the Adler-32 checksum in the zlib trailer
did not match the bytes that came out:

```text
boyko-W2602: zlib Adler-32 mismatch (expected 0x00420042, got 0x00000000); decoded pixel data may
still be usable, continuing
```

Raised from `crates/boyko_image/src/inflate.rs`, once per decompressed stream. The inflated bytes
are returned and the image decodes from them.

## Why

Unlike a chunk CRC, the Adler-32 covers the **whole** stream, so a mismatch says "some byte in this
image is wrong" without saying which. That is precisely why it is not an error: the decoder cannot
tell whether the damage is one pixel in a corner or the entire surface, and refusing the image would
turn a possibly-cosmetic corruption into a missing texture. Returning the bytes with a warning
leaves that judgement to whoever is looking at the result.

`RatePolicy::Every`: one report per decompressed stream, at load time, never per frame.

### A note for anyone writing PNG fixtures

Until rung L8a, `boyko_image`'s own test fixtures were built with a deliberately wrong Adler-32
trailer, on the reasoning that "a mismatch is a non-fatal warning by design, so tests need not
duplicate the checksum algorithm". The consequence was that roughly twenty decode tests silently
exercised the corrupt-stream path, which was invisible while the warning was an `eprintln!` nobody
counted - and became measurable interference the moment it became a counted record. If you hand-roll
a fixture, compute the real checksum; leave exactly one fixture wrong, on purpose, to test this
code.

## How to fix

- **Re-export or re-download the asset.** As with `boyko-W2601`, a truncated or partially-written
  file is the usual cause.
- **Look at the decoded image before assuming it is broken.** A mismatch with visually correct
  output means the damage is in bytes the expansion path did not use, or the encoder simply wrote a
  wrong trailer - some minimal PNG writers do.
- **If you see this together with `boyko-W2601` on the same file**, treat the file as corrupt rather
  than the writer as sloppy: two independent checksums disagreeing is unlikely to be a tooling
  quirk.
