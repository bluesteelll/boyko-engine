# boyko-B0002 — intra-system access conflict on one resource

## What happened

Two `SystemParam`s of the **same** system asked for accesses to one resource that cannot coexist —
`ResMut<R>` beside `Res<R>`, or `ResMut<R>` twice. The conflict is detected while the system's
parameters register their access, before the system has ever run:

```text
boyko-B0002: intra-system access conflict on resource id 7.
Existing param: ResMut<Config>
Conflicting param: Res<Config>
Kind: WriteVsRead
This would be UB at runtime. Remove one of the accesses or use the same mutability.
```

Raised from `crates/boyko_ecs/src/ecs/core/system/params/diagnostics.rs`
(`intra_system_conflict_panic`), reached from `Res<R>::init_access` / `ResMut<R>::init_access`.

## Why

`Res<R>` and `ResMut<R>` hand the system body a `&R` and a `&mut R` **into the same slab entry**.
Holding both at once is aliasing UB in the Rust sense, not merely a logical mistake — the compiler
is entitled to assume the `&mut` is unique and to reorder or elide loads accordingly.

The check is at **access registration** rather than at first dereference for the reason the message
gives: the failure it prevents is UB, and UB does not reliably announce itself. A system that
aliased a resource might run correctly for a year and then miscompile after an unrelated inlining
decision. Registration is the last moment at which the conflict is a fact about the *declaration*
rather than about a particular execution.

It is a **panic and not a `Result`** because there is no recovery: the parameter tuple is part of
the system's type, so the conflict cannot be repaired at run time — only by editing the signature.

## How to fix

Decide which access the system actually needs and keep one:

- **It reads and writes.** Take `ResMut<R>` alone; `&mut R` derefs to `&R` wherever a read is
  wanted.
- **Two params want it for different reasons.** Split the system, or pass the value through a
  local: one `ResMut<R>` at the top and ordinary Rust borrows below it.
- **The two params are generic and collided by accident** — `Res<A>` and `ResMut<B>` where `A` and
  `B` monomorphised to the same type. The message prints the resource **id**, which is what
  disambiguates the two spellings.

Interior mutability is not a workaround: the conflict is about the reference the world hands out,
and `ResMut<R>` still yields `&mut R` around a `Cell`.
