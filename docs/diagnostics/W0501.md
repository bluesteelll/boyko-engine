# boyko-W0501 — the query-type table is three quarters full

## What happened

A distinct `Query<D, F>` shape was seen for the first time, and minting its id took the
process-global query-type table past 75 % occupancy:

```text
boyko-W0501: the query-type table is 768 of 1024 slots used (75 %); at 1024 the next distinct
             Query<D, F> shape is a terminal panic (boyko-B0502) -- enable the `big_query_table`
             feature or consolidate query shapes
```

Raised once per process from
`crates/boyko_ecs/src/ecs/core/iters/query/query_type_registry.rs` (`register_new`).

## Why

Every distinct `(D, F)` pair burns one slot, permanently, the first time it is seen — a `QueryTypeId`
is never recycled, because the id indexes eagerly-allocated per-world slot arrays and reuse would
alias two shapes onto one memo.

Without this warning the table's only observable behaviour was **1023 silent mints followed by a
process kill**. The exhaustion panic (`boyko-B0502`) is correct and unhelpful on its own: by the
time it fires, the shape that happened to be last is named, and the 1023 that filled the table are
not. A title that grows its query surface gradually crosses this line long before it crosses the
other one, and the gap is where the cheap fix lives.

75 % rather than a fixed remaining count, because what matters is the **rate** relative to the cap:
a codebase at 768 of 1024 is one refactor away from the wall whether the cap is 1024 or 4096.

## How to fix

Two answers, and which is right depends on whether the shapes are real.

- **The shapes are real** — a large title legitimately has many distinct `Query<D, F>` types.
  Enable the `big_query_table` feature on `boyko_ecs`, which raises the cap from 1024 to 4096. The
  cost is the per-world slot arrays, which scale with the cap.
- **The shapes are accidental.** Generic helpers instantiated over many component types mint one id
  per instantiation, and a helper that takes `Query<&T, With<Marker>>` for forty `T`s spends forty
  slots on one piece of logic. Consolidating on a shared shape — or moving the type parameter out
  of the query and into the body — recovers them.

The count in the message is the occupancy **after** the mint that crossed the line, so it is a
measurement rather than a threshold restated. This fires once per process; the number does not
update as the table fills further.
