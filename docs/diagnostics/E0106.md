# boyko-E0106 - a dynamic target could not be registered

## What happened

`boyko_log::target::register_dynamic_target` returned `None`, so the caller has **no `TargetId`**
and every `dyn_*!` call it was going to make is now a no-op:

```text
boyko-E0106: dynamic target mod:acme_weapons refused: the 32-slot band is full
boyko-E0106: dynamic target  refused: the name is empty
boyko-E0106: dynamic target xxxxx...xxxx refused: the name is longer than 47 bytes
```

Raised from `crates/boyko_log/src/target.rs`. The process continues; the registering module's
logging simply never appears.

## Why

The dynamic band is ids `224..=255` — **32 slots, `.bss`, one cache line each, never released.**
There is no growth path by construction: a table that reallocated would put an allocation on the
one structure whose whole argument is that it makes none, and a table that evicted would invalidate
a `TargetId` some other module is already holding.

**One code covers three refusals**, with the reason as an argument:

| reason | what it means |
|---|---|
| `the 32-slot band is full` | 32 distinct names are already interned |
| `the name is empty` | `len == 0` is the slot's *free* marker, so an empty name could not claim one even in principle |
| `the name is longer than 47 bytes` | 64 − 8 (`hash`) − 1 (`len`) leaves exactly 47 |

They are one function's one failure return and a caller cannot act differently on them, so three
codes would be three names for one event. The **design corpus documents only the first** — the
signature comment in `04-GAME-FACING.md` reads *"`None` => band exhausted"* — which is narrower
than the function it annotates. A caller who believed it would read a rejected 60-byte name as a
lost band, stop registering, and lose every target after it. Hence the reason string.

`RatePolicy::Every`, not `Once`. Once the band is full **every** later registration fails, and each
failure is a different module whose logging is now silently absent; a latch would name the first
victim and hide the rest. This is the same argument `W0901` records for its component types.

**This is one of the few places `boyko_log` logs about itself.** `W0103` writes through `sync_out`
because the file sink cannot log into itself; nothing like that applies here — the dynamic band sits
beside the emission path rather than underneath it, and the target this emits on (`log`) is a static
engine row that a failed dynamic registration cannot have disturbed.

**A default run shows nothing**, exactly as at every other migrated site: with `BOYKO_LOG` unset the
`log` target's runtime ceiling is `Off` and the `error!`'s third gate folds. There is no `stderr`
fallback here, because the fallback is reserved for sites where the process is stopping and the
record *is* the reason — see `E0201`, `E3002`, `E3003`. A refused registration is not terminal.

## How to fix

- **Count your registrations.** 32 is the whole band for the process, shared by every module. A
  system registering one target per *entity*, per *asset*, or in a loop has the wrong granularity:
  a dynamic target is a **category** (`"mod:acme"`), not an instance.
- **Register once, at setup, and keep the `TargetId`.** Registration is idempotent by name, so a
  re-registration is not what exhausted the band — 32 genuinely different names did.
- **Check the name before you pass it.** Empty and over-47-byte names are caller bugs the boundary
  catches; they consume no slot and leave no partial state, so fixing the string is the whole fix.
- **`find_target(name)` searches both bands** and does not consume a slot. A module that only wants
  to *address* a target somebody else registered should use that instead.
- **`dyn_registered()` reports occupancy** — worth asserting at the end of your own setup if you
  ship a mod host and want the exhaustion to surface as your failure rather than as silence.
