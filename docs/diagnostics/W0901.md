# boyko-W0901 - a dense store carried no decodable data, so its members were skipped

## What happened

A save file's dense-store section contained a block for a component this build cannot decode, so
the block's memberships were dropped and the load continued:

```text
boyko-W0901: dense store for component `Velocity` carries no decodable data (Ignore, or
SerializeViaFn with no installed deserialize_fn); skipped 12 member(s) (recorded in
LoadReport::dense_stores_skipped)
```

Raised from `crates/boyko_serialize/src/load.rs`. Two conditions produce it, and the message names
both because the site cannot tell them apart at that point:

- the component's `Serializability` is `Ignore` - by contract it carries no decodable data;
- it is `SerializeViaFn` and **no `deserialize_fn` is installed** in this process.

The owning entities are still created and are still valid. What they do not get is this component's
dense membership, and therefore its value.

## Why

`LoadReport::dense_stores_skipped` and `dense_members_skipped` have counted this since the dense
plan landed, and that was the whole signal: **a number, with no name attached.** A host that logs
totals - or drops the `LoadReport`, which is a plain return value - could not tell which component's
data had vanished, or that any had.

`RatePolicy::Every`, deliberately: the subject of this record is a **component type**. A save
carrying three undecodable dense stores has three different things to tell you, and a `Once` here
would name one of them and silently lose the other two names.

**It stopped being `#[cfg(debug_assertions)]` at rung L8a.** The reporter had a release no-op beside
it, justified by "the `LoadReport` counters carry the signal there". They carry a count; the release
build is also the one where a silently-lost component matters most. Un-gating costs a release build
one `#[cold]` call on a path that had already incremented two counters on the line above.

## How to fix

Work out which of the two conditions you are in - the message does not distinguish them, but your
component's registration does:

- **`Ignore` was intended.** Nothing to fix. The component is declared non-serializable and the
  save round-trips exactly as designed; filter the code if the volume is noisy.
- **`SerializeViaFn` with no decoder.** This is the real defect the code exists to surface: the
  save wrote memberships expecting a decoder that this process never installed. Install the
  `deserialize_fn` for that component before loading, in the same place its serializer is
  registered. A load that runs before registration completes produces exactly this line.
- **You did not expect that component in the file at all.** Then the save came from a build with a
  different component set, and the skipped members are the honest outcome; compare the two builds'
  registrations rather than the file.
