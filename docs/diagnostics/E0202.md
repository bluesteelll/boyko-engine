# boyko-E0202 — a scope task's panic payload was discarded instead of delivered

## What happened

A task spawned into a `ThreadPool` scope panicked, and its payload could not be handed to the
thread that joins the scope. The pool recorded that fact and dropped the payload:

```text
boyko-E0202: a scope task's panic payload was discarded (<reason>) and is not propagated
```

Raised from `crates/boyko_threadpool/src/scope.rs` (`discard_payload`). The reason is one of
three, and they are not the same event:

| reason | what it means |
|---|---|
| `a later panic lost the first-wins CAS` | two tasks of one scope panicked; the first published its payload and this is the second. The documented protocol — the caller receives one payload, not a list |
| `the owner thread was already panicking` | the scope's **own** closure (the one passed to `install`/`scope`) panicked, and a task raised too, so the scope is being dropped by that closure's unwind. The owner's payload wins and reaches its caller; this one is recorded here |
| `the scope was dropped without collecting it` | a `ScopeShared` was dropped without the `take_panic` hand-off. Reachable from the loom test wrapper, not from the shipped join |

The panic's own message was printed by the default hook at the unwind's origin, before the pool
saw it. This line records the **decision**, not the cause.

## Why

A scope delivers **one** payload to **one** joining thread, and both halves of that sentence force
a discard somewhere.

Two tasks that panic in one scope are two payloads and one caller. `Vec<Box<dyn Any>>` aggregation
was considered and rejected: it allocates on the panic path and changes the return shape of a hot
fork/join API for a case whose second payload nobody reads. First-wins is rayon's rule and the
protocol this pool documented before the payload slot became lock-free.

The already-panicking case is sharper, and it is the one this code exists for. `Scope::drop` runs
during the owner's unwind; a `resume_unwind` there is a panic inside a cleanup pad, which Rust
turns into `thread caused non-unwinding panic. aborting.` — the whole process, for two panics that
each had somewhere to go. `std::thread::scope` resolves the same collision the same way: the
body's panic has the causal position and wins.

The test is on the scope's own closure, not on `std::thread::panicking()`. A scope whose closure
returned re-raises its task's panic even while an outer frame of the same thread is unwinding —
which happens when a join inside another scope's unwind runs queued work inline, and that work
opens a scope of its own. Discarding there would let `install`/`scope` return normally over a task
that never finished; this reason is therefore never emitted for a scope whose closure returned.

The discard itself is performed inside a `catch_unwind` **together with this record**, because a
payload whose own `Drop` panics (rust#86027) would otherwise unwind out of a cleanup pad and abort
the process.

## How to fix

The panic is the defect; the discard is the report.

- **Read the panic printed above this line.** With two panicking tasks, the payload the caller
  receives is the *other* one, so the log may name a failure the caller never sees.
- **If you need every failure, do not use panics for it.** Have the task body return a `Result`
  into a per-task slot you own, and inspect all of them after the scope closes.
- **If the reason is `the owner thread was already panicking`**, fix the owner's panic first: it
  is the one that reached your caller, and it may well be what made the task fail.
