# boyko-W0103 — the file sink reached its byte cap

## What happened

The log file sink was opened with a byte cap, the next line would have crossed it, and the sink
**stopped writing**. It printed one line to the synchronous channel and nothing further:

```text
boyko-W0103: file sink reached its 1048576-byte cap; no further lines are written
```

Raised from `crates/boyko_log/src/sink/file.rs` (`report_cap`).

## Why it is a warning and not an error

Nothing is broken. The cap is a limit the host asked for, and reaching it is the limit doing its
job. What makes it worth a code at all is the *silence that follows*: from this point the file is
a truthful record of the beginning of the session and says nothing about the rest, and a reader
who does not know that will read the last line in the file as the last thing that happened.

## Why it does not go through the emission path

This condition is "the destination is full". A record about it, routed normally, would be routed to
the destination that is full — so it takes the synchronous channel instead, which is the same
channel a laneless thread's `Warn` takes and the same one the crash path uses. It is subject to the
same honest limit as every other user of that channel: with no synchronous destination configured,
it reaches nothing (see `logging/sink-lifecycle`, Decision 9c).

## Why it fires once

`RatePolicy::Once`, with a site-local latch rather than a shared `RATE` slot. There is exactly one
site, so per-site and per-code coincide here — but the latch is still where the policy says it
belongs, because the moment a second site appears the two answers stop being the same. The steady
state after the first fire is one `Relaxed` load and **no store**.

## What it does NOT do

- It does not truncate, delete or roll over the file. Rotation is a separate mechanism with its own
  code (`boyko-W0112`); a sink that discarded the beginning of a capture in order to keep writing
  would destroy exactly the records that explain the ones it kept.
- It does not stop the rings, the console route or the ECS handoff. Only this destination is short.
- It does not stop the process, and it does not fail a launch.

## How to fix

- **Raise or remove the cap.** `LogConfig.file_cap_bytes` is the knob; `0` means uncapped.
- **Reduce what reaches the sink.** Lower a noisy target's runtime level, or give a repeating code
  a `RatePolicy::EveryN` / `MinIntervalMs` row so the volume is damped at the source rather than at
  the destination.
- **If you wanted the tail rather than the head**, a cap is the wrong tool — you want rotation, and
  until it lands the honest answer is an uncapped file plus a size check outside the process.
