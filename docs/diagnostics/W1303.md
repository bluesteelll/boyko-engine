# boyko-W1303 - the self-collision spatial hash is overloaded, so bucket chains are long

## What happened

The self-collision spatial hash was built with far more particles than buckets:

```text
boyko-W1303: SP3 self-collision load factor pathological -- 1024 particles in 8 buckets (expected
~0.5; bucket chains will be long)
```

Raised from `crates/boyko_physics/src/soft/self_collision.rs`, once per
`resolve_self_collision` call, after the table is built. The pass still produces correct results -
the CSR scan visits every candidate either way - but the candidate scan degenerates toward
quadratic, so the step gets slower in proportion to how far past the threshold you are.

## Why

The table size is `next_pow2(2n)`, which puts the load factor at about `0.5` **by construction**.
A body that reaches `n > 4 * table` therefore does not have a tuning problem; it has an
inconsistency between its particle count and its preallocated scratch columns - a body assembled by
hand, or one whose `sc_cell_start` / `sc_cell_items` / `sc_cursor` were sized against a different
`n`.

The check is two compares (`table != 0 && n > 4 * table`) evaluated **once per call**, not per
particle, on a path that has just run `next_pow2` and built the whole hash. That is why rung L8a
dropped its `#[cfg(debug_assertions)]`: the cost is unmeasurable and the condition is a real
performance cliff that a release build previously hit in silence. Compare `boyko-W1302`, which
kept its gate because its condition needs an O(constraints) scan.

`RatePolicy::Once`, per site: the condition persists for as long as the mismatched body does, and
one report per substep would drown the log it is trying to inform.

## How to fix

- **Rebuild the body through `SoftBody::from_mesh`**, which sizes the self-collision scratch from
  the particle count. This is the fix in almost every case: the constructor and the table size
  cannot disagree.
- **If you assemble a `SoftBody` field by field**, size `self_table_size()` to `next_pow2(2n)` and
  the three scratch columns to `table + 1` / `table + 1` / `n`. The debug build asserts these
  shapes; this warning is what a release build says instead.
- **If the particle count changed after construction**, re-run the sizing. Growing a body without
  regrowing its hash scratch is the commonest way to reach this state.
