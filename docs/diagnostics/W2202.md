# boyko-W2202 - a bindless table exhausted its slots and aliased its reserved fallback slot

## What happened

A bindless slot allocator ran out of free slots, so the registration returned the reserved
slot-0 instead of a real one:

```text
boyko-W2202: bindless table `BindlessTextureTable` exhausted its 4096 slots -- aliasing reserved
fallback slot 0 instead of writing out of range
boyko-W2202: bindless table `MeshGeometryTable` exhausted its 1024 slots -- aliasing reserved
fallback slot 0 instead of writing out of range
```

Two sites share this code, one per table, and the table's name is the argument that tells them
apart. Slot 0 is the magenta error texture in the first case and the all-zero degenerate geometry
row in the second, so the visible result is a magenta surface or a mesh that draws nothing - not a
crash and not an out-of-range descriptor write.

## Why

Aliasing the reserved slot is the safe outcome of a condition that should be unreachable: both
tables are sized well above any real asset count, and the `debug_assert!` beside this report fires
first in a debug build. In release the assert compiles out, and before rung L8a what remained was
an ad-hoc `eprintln!` prefixed with a hand-written `"WARN: "` - a severity invented at the call
site on a channel that carried none.

**The two sites keep separate `Once` latches, and that is the point of the policy being per site.**
A code-scoped latch would let whichever table exhausted first silence the other's only report,
uncounted, because `Once` deliberately does not count its suppressions. The cost is two nearly
identical `#[cold]` functions rather than one shared helper - a shared helper taking a `&OnceSite`
would read as though the latch were shared, which is the thing that must not happen.

## How to fix

This is almost always a leak rather than a capacity problem, because both capacities are large:

- **Check the fence-gated recycle is draining.** Freed slots are staged in `retiring_slots` and only
  returned once `retire_ready_slots(epoch)` observes the epoch has passed. If nothing calls it -
  `asset_refcount::retire_deferred_frees` is the engine's caller - slots are freed and never come
  back, and the table exhausts at exactly the rate you load and unload assets.
- **Check for repeated registration of the same asset.** Registering a texture or mesh per frame,
  rather than once per asset, consumes a slot each time.
- **If the count is genuinely legitimate**, raise the table's capacity: `BINDLESS_TEXTURE_CAPACITY`
  for the texture table, `VulkanGeometryBindlessSet::capacity` for the geometry table. Both are
  paired with a device descriptor-count limit, so check `maxDescriptorSetUpdateAfterBindSampledImages`
  before raising either.
