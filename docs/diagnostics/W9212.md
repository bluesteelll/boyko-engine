# boyko-W9212 — `register_zone` refused an engine scope

## What happened

A `ZoneSpec` asked for a scope inside the engine's reserved range, and the registration was
refused:

```text
boyko-W9212: register_zone refused a scope below 32; scopes under that are the engine's
```

Raised inside `boyko_diag::profiling_abi::dyn_registry::register_zone` as
`DiagFlag::EngineScopeRefused`; emitted from
`crates/boyko_ecs/src/ecs/core/profiling/diag.rs` (`report_engine_scope_refused`). The caller also
gets `RegisterError::EngineScope` — this code is the once-per-session report, not the answer.

## Refused, not clamped — and that is the decision

The obvious alternative is `scope.max(USER_SCOPE_BASE)`: nudge the zone into the user range and
carry on. It is rejected for a reason that only shows up later, when it is expensive:

A scope is an **arming knob**. A zone silently moved to a neighbouring scope is armed and disarmed
by a switch nobody pointed at it — so it appears when an unrelated subsystem is enabled, vanishes
when that one is turned off, and its samples arrive interleaved with that subsystem's under a scope
name that describes neither. The registration failing loudly at the manifest that caused it is
strictly cheaper than a measurement that is wrong in a way nothing downstream can detect.

## Where the line is, and what it does and does not guarantee

`USER_SCOPE_BASE = 32`. Scopes `0..32` are the engine's; `32..SCOPE_COUNT` are a game's.

⚠️ **This is enforced on the dynamic path and is a convention on the static one.** `declare_zone!`
takes a scope *expression*, and no macro can evaluate it — so a `User` crate can still declare a
static zone on scope 3. What the design's isolation actually rests on is elsewhere and is
structural: the **id space** and the **ring region**, both keyed on the declaring crate, so a game's
zones can neither consume the engine's ids nor fill the engine's ring. The scope split is the
narrower property that a game's arming knob does not also arm the engine's zones, and it is enforced
at the one entry point that takes a scope as a run-time value.

Stated plainly because "scopes below 32 are the engine's" reads like a guarantee and is one only
here.

## A scope past the mask is refused by the same check

`SCOPE_COUNT` is 64 and the arm mask is a `u64`, so a scope at or above 64 has no bit to precompute
— `1 << scope` would be undefined. `register_zone` refuses it through the same arm rather than
wrapping it into a bit that belongs to someone else.

## How to fix

- **Pick a scope in `32..64`.** If the data is authored (a mod manifest, a config file), the scope
  is data too, and the fix belongs there.
- **If the zone genuinely belongs to the engine**, it should be a static `declare_zone!` in an
  engine crate, not a dynamic registration. `register_zone` exists for zones whose *names* are data;
  a zone the engine owns has a name at compile time.
