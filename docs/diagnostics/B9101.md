# boyko-B9101 — `Schedule::run` was given a different world than the one it was built on

## What happened

A `Schedule` built against one `EcsMaster` was run against another:

```text
boyko-B9101: Schedule::run called with a different world than the one it was built on
             (built on WorldId(0), got WorldId(1)) — a Schedule is bound to the world it was
             built on; build a separate Schedule per world
```

Raised from `crates/boyko_ecs/src/ecs/core/schedule/schedule.rs`
(`schedule_world_mismatch_panic`), a `#[cold]` out-of-line site so the run entry carries only the
compare and a never-taken branch.

## Why

A built schedule is not a list of systems — it is a plan resolved **against a specific world's
identifier space**. Component ids, resource ids, archetype ids and query-type ids are all minted
per world, and the schedule caches them: system access sets, the conflict matrix that decides what
may run in parallel, and every `SystemParam`'s resolved state.

Running that plan against a different world does not fail loudly on its own. The ids are still
valid *integers*, so the systems would read the second world's resources through the first world's
id assignment — silently returning another type's data, or another archetype's rows. The check
exists precisely because the failure it prevents is quiet.

It is **release-live**, not a `debug_assert!`: an invariant whose violation is a wrong answer
rather than a crash must hold in the build that ships. The cost is one comparison per `run`.

## How to fix

Build a schedule per world:

```rust
let sched_a = ScheduleBuilder::new().add_system(..).build(&mut world_a);
let sched_b = ScheduleBuilder::new().add_system(..).build(&mut world_b);
```

The builder is cheap to describe twice; what is expensive is the resolution, and that is the part
that cannot be shared.

If you are here because a schedule is stored in a long-lived struct beside a world that gets
replaced — on a level load, or a reset — rebuild the schedule at the same moment the world is
replaced. A schedule outliving its world is the common shape of this bug, and it is the reason the
message prints both ids: the built one tells you which world it was resolved against.
