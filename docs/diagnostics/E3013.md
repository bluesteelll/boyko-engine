# boyko-E3013 — a device loss was diagnosed, and the GPU crash report follows

## What happened

The frame loop met `VK_ERROR_DEVICE_LOST` (reported first as `boyko-E3003`), and the engine read
back what its GPU crash diagnostics recorded. The report is up to 16 bounded lines, each its own
record:

```text
boyko-E3013: device lost at render (VK_ERROR_DEVICE_LOST); GPU crash report: level=checkpoints pieces=fault,labels,markers,checkpoints profile=dev
boyko-E3013: slot 1 serial 9 declarator deferred passes 6: last completed #2 ssao_atrous#0; in flight: #3 ssao_atrous#1, #4 ssao_atrous#2; not started: 2 (first #5 resolve)
boyko-E3013: slot 0 serial 8 declarator deferred passes 6: frame complete (7 scopes)
boyko-E3013: checkpoints (2): TOP_OF_PIPE -> serial 9 begin #4 ssao_atrous#2; BOTTOM_OF_PIPE -> serial 9 end #2 ssao_atrous#0
boyko-E3013: device fault: "MMU fault"; addresses 1; vendor records 1; vendor binary 64 B
boyko-E3013: fault address 0: write-invalid 0x12345678 [0x12345000..0x12345fff]
boyko-E3013: fault vendor record 0: code 0xc0 data 0xda7a "MMU fault"
boyko-E3013: vendor binary: 64 B, vendor 0x10de device 0x2c02 driver 0x99887766 uuid … -> ./boyko-gpu-fault-<unix_s>-<pid>.bin
boyko-E3013: note: scopes overlap where no barrier orders them, so the in-flight set is a SET, not a culprit; …
```

Raised from `crates/boyko_app/src/diag.rs` (`report_gpu_crash_if_device_lost`), after `E3003` at
the frame loop's two terminal sites (`frame fence wait`, `render`). The data comes from
`Renderer::device_lost_report` (`crates/boyko_rhi_vulkan/src/present/gpu_crumbs.rs`).

What each line means:

- **A slot line** is one frame-in-flight slot's last armed frame. Every graph pass and every
  hand-recorded host step (FXAA, SMAA, the present blit) runs inside one GB scope that wrote a
  begin breadcrumb at `TOP_OF_PIPE` and an end breadcrumb at `BOTTOM_OF_PIPE`. *Last completed* is
  the last record position whose begin and end both landed; *in flight* is every position whose
  begin landed and whose end did not; *not started* counts the rest. A pass name that repeats in a
  frame carries its ordinal (`ssao_atrous#2` is the third `ssao_atrous` of the frame).
- **checkpoints** are NVIDIA's per-stage last checkpoint (`VK_NV_device_diagnostic_checkpoints`),
  written at the same scope points.
- **device fault** is the driver's own record (`VK_EXT_device_fault`): a description, the faulting
  addresses with their precision range, vendor records, and a vendor binary written to a file.

## Why

Before this report the whole account of a device loss was one `E3003` line naming a Vulkan result.
A GPU hang or page fault is the defect class where a reproduction is most expensive and a capture
tool least able to help, so the engine records, at a cost of one predicted branch per scope when
disarmed, which scope the GPU was inside.

**The report is a hint, not a verdict, and says so.** Scopes overlap wherever no barrier orders
them, so the in-flight entry is a SET — the culprit is one of them or something they waited on.
The spec leaves marker contents after a device loss undefined, and a write cache may not have
flushed. A slot whose frame is complete or not started, in both slots, points away from the frame:
the report then says the loss is likely in an upload or readback submission on the same queue.

**Only the two frame-loop sites report.** A loss that surfaces first in an upload or a readback
path ends in that path's own error, without this report.

`RatePolicy::Every`, one record per line; like `E3003` it writes to `stderr` when there is no log
consumer, because the run is over and nobody asked for a log.

## How to fix

- **Arm the diagnostics before reproducing.** The level is `BOYKO_GPU_CRASH_DIAG`
  (`off|fault|labels|markers|checkpoints`, cumulative) or the `GpuCrashDiag` resource, read once at
  boot. `markers` gives the in-flight set; `checkpoints` adds NVIDIA's per-stage view. A `shipping`
  build compiles all of it out (`GPU_CRASH_DIAG_CEILING = 0`); use a `dev` or `editor` build.
- **Start from the in-flight set.** Read those passes' shaders for an unbounded loop, an
  out-of-range index or a dispatch sized past its buffer; a fault address inside a known buffer's
  range names the resource.
- **Keep the vendor binary.** It is written to `$BOYKO_GPU_CRASH_DIR` (or the current directory).
  It is vendor-defined after its 56-byte header; send it with the driver version to the vendor.
- **Re-run with validation** (`BOYKO_ENABLE_VALIDATION=1`): a hang usually has a validation error
  earlier in the same run.
- A device that lacks a piece printed `boyko-W2107` at boot; the matching report line then says
  "not armed" or "unavailable".
