# `boyko-W1803` — a launch flag named a runtime preset the table does not carry

**Class:** `W` (the engine did something the caller probably did not intend)
**Rate:** `Every`
**Emitted by:** `crates/boyko_app/src/plugins.rs`, on the host's boot path

## What happened

`BOYKO_LOG_PRESET` was set to a value that is not one of the five names
[`LogRuntimePreset::name`](../crates/boyko_log/src/preset.rs) prints:

```
dev · editor · shipping · shipping-min · off
```

The host fell back to its hand-built configuration — console on, no file, a resident sink thread —
and the session header therefore reads `runtime_preset=custom`.

## Why it is a warning and not a silent fallback

The fallback is a working configuration, so nothing breaks. What breaks is the operator's belief:
someone who typed `shiping` gets a run whose header says `custom`, and `custom` is also what an
ordinary un-flagged run says. Without this record the two are indistinguishable, and the reader most
likely to be misled is the one who set the flag.

## Why `Every` and not `Once`

Each occurrence names a **different** mistyped value. A latch would report the first launch flag
anyone got wrong and silence every later one — the `W2102` failure at a different scale. In practice
the site runs once per process, which is a fact about the caller rather than a policy the registry
should state.

## How to fix

Set one of the five names, or unset the variable. The names are deliberately the same strings the
header prints, so a run can be reproduced from its own log rather than from a memory of how it was
launched.

Two companion variables are read only when the preset parses:

| variable | effect |
|---|---|
| `BOYKO_LOG_FILE` | the text sink's path, for the rows whose destination is a text file |
| `BOYKO_LOG_BLOG` | the binary sink's path, for `shipping` |

`BOYKO_LOG` still narrows the level afterwards, so the two knobs compose rather than one silently
winning.
