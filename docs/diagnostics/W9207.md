# boyko-W9207 — no invariant TSC

## What happened

The profiler armed on a CPU that does not advertise an invariant TSC (`CPUID.80000007H:EDX[8]`):

```text
boyko-W9207: no invariant TSC: profiling tick magnitudes are not trustworthy across cores or power states
```

Raised from `crates/boyko_ecs/src/ecs/core/profiling/diag.rs` (`report_no_invariant_tsc`), once, at
`Profiler::arm`.

## This is the ENGINE's single invariant-TSC code

Both subsystems read one clock — `boyko_diag::clock` — so both have one answer to give about it.
The logging plan carried its own `W0101` for this condition and it was **struck in favour of this
code**: an uncontrolled code in one plan and a controlled one in the other, for one condition, is
two answers to one question.

## What it actually costs

Without an invariant TSC the counter may run at a rate that changes with frequency or C-state, and
may not be synchronised between cores. Three consequences, in order of how much they matter:

1. **Magnitudes are unreliable.** A span's tick count converts to nanoseconds through a scale
   probed once; if the rate moved since, the number is wrong by however much it moved.
2. **Cross-core intervals may be nonsense.** A span opened on one worker and closed on another can
   read negative or absurdly large.
3. **Ordering within one core still holds.** Attribution — which frame a sample belongs to — is a
   comparison of stamps taken on the same core in the same epoch, and survives.

`boyko_diag::clock` falls back to a QPC-derived tick on such a machine, so the numbers are still
*monotone*; what is lost is the claim that a tick is a fixed unit of time.

## Why it is a warning and not an error

The session runs and the profile is produced. A contrast between two legs taken minutes apart on
such a box is what should not be trusted, and the code is what tells a reader to distrust it.

## Where it can and cannot be observed

**Named rather than smoothed:** on every x86-64 machine this project targets, `invariant_tsc()`
returns `true`, so this code has **no reachable emission on the development box**. What is tested
there is the *selection* — `diag::clock_code(false) == Some(9207)` — which reds if the mapping is
deleted. The emission itself is `UNPROVEN` on this hardware and is stated as such rather than
recorded as covered.

## How to fix

There is nothing to fix in the engine. If the numbers matter on such a machine:

- Pin the measured process to one core, so cross-core comparison does not arise.
- Disable frequency scaling and deep C-states for the sitting.
- Prefer contrasts taken in **one sitting**, interleaved, over contrasts across sittings — which is
  the protocol this project already requires for a different reason.
