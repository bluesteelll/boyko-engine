# boyko-W3007 - the VB geometry table could not be created

## What happened

`MeshGeometryTable::new` failed at boot, and the visibility-buffer geometry leg is off:

```text
boyko-W3007: MeshGeometryTable::new failed (<the error>) - the VB geometry table is disabled
```

Raised from `crates/boyko_app/src/runner.rs`. The engine keeps running: `MeshGeometryTableSlot` is
set to `None`, and every consumer of the table checks the slot.

## Why

The table is the bindless geometry side of the visibility-buffer path - the per-mesh vertex,
index and attribute descriptors the VB classify and shade passes index by draw. It is built once at
boot from the device's descriptor-indexing limits, and it is *optional* by construction, which is
why this is a `Warn` and not `boyko-E3002`'s boot failure: a host without it renders every other
path unchanged and renders VB without its geometry leg.

**A `warn!` rather than a silent `None`.** Absent, the failure surfaces later as a VB frame that
draws nothing, at a distance from its cause - which is the shape of bug this campaign keeps finding
and the reason a degrade is reported at the moment it is taken.

`RatePolicy::Once`, per site. The table is built once per boot, so the latch is a `Relaxed` load
and a second occurrence cannot exist in one process.

## How to fix

- **Check descriptor-indexing limits.** The table asks for a descriptor count derived from the
  scene's mesh budget; a device whose `maxDescriptorSetUpdateAfterBindStorageBuffers` is below it
  refuses here. The carried error names the Vulkan result.
- **`VK_ERROR_OUT_OF_DEVICE_MEMORY`** at this stage means the boot allocations before it already
  took the heap - the render targets and the SSAA ring are the two large ones, and
  `boyko-W3005`'s `heap=` figure is the number to compare against.
- **If VB is not being used**, this warning is informational: the deferred and forward paths do not
  read the table, and the slot being `None` costs them nothing.
