# boyko-W2201 - more lights are enabled than the GPU light table holds

## What happened

The per-frame light fold hit its hard cap and stopped writing:

```text
boyko-W2201: light table overflow -- more than MAX_LIGHTS (256) enabled lights; the 256 rows
already written are kept and every later light is dropped from the GPU table
```

Raised from `crates/boyko_render/src/light_system.rs`. The frame renders. The rows already written
reach the GPU and light the scene; every light the fold had not yet reached is simply absent, and
which ones those are depends on the fold's fixed order - directionals, then sky, then points, then
spots.

## Why

The GPU light table's body region holds exactly `MAX_LIGHTS` `GpuLight` slots and the saturating
gate (`written == MAX_LIGHTS`) is checked before each write, in **all** build profiles. Without
that gate a scene with too many lights would write past the buffer; with it, the excess is dropped
and this code says so.

**The record does not carry a count of what was dropped, and the omission is deliberate.** The
migration ledger asked for one. It is not obtainable here: `fold_light_table_slotted` takes
`impl Iterator`s, its contract pins "walked exactly once each", and the overflow path *returns* -
so at the moment of the report nothing has looked at the remainder, and counting it would mean
draining iterators the contract says are not drained, on the overflow path, purely to produce a
number. What the site does know is the cap it hit and how many rows made it, so that is what it
reports.

**This is a different code from `boyko-W2204`**, which reports lights dropped for carrying a NaN.
Both are `Warn`, both mean "a light you enabled is not in the render" - and they need different
fixes, which is what makes them two codes rather than one with an argument. `W2204` does carry a
real count, because at that site one exists.

`RatePolicy::Once`, per site: the fold runs every frame, and a scene that is over the cap is over
it on every one of them.

## How to fix

- **Reduce the number of enabled lights.** `IsEnabled`/`EnableTag` on a light is a structural skip:
  disabling the ones outside the play area costs nothing per frame and is the intended lever.
- **Check what is actually enabled.** The header counts (`l0a_count`, `point_spot_count`) written
  into the table tell you the split between directional/sky and punctual rows; a scene that
  overflows on directionals alone is usually an authoring accident.
- **If you genuinely need more**, `MAX_LIGHTS` is a compile-time constant paired with the shader's
  own table size and the clustered-cull froxel budget. Raising it is a coordinated change across
  `crates/boyko_render/src/light.rs` and the lighting shaders, not a single constant.
