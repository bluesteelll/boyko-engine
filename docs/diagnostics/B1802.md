# boyko-B1802 - an App config method was called after finish()

## What happened

A configuration method was called once the `App` had entered its run phase:

```text
boyko-B1802: App::add_systems_in called after finish() — the App is in the run phase; perform all
configuration before the first finish()/update()/run() call
```

Raised from `crates/boyko_ecs/src/ecs/core/app/app.rs`, in `config_after_finish_panic`. Every
config method routes here through `App::assert_config_phase`, so the method's own name is carried
as an argument.

## Why

`App::finish` is the point of no return, and it is one because of what it does: it **consumes the
staged builders**, drains the startup queue and resolves the config staging into the live schedule.
After it, there is no staging left for a registration to land in.

So a post-`finish` `add_systems_in` could not take effect no matter what the `App` did with it.
The only two options are to panic or to accept the call and silently drop it - and dropping it
produces a system that is in the source, is never scheduled, and is never reported. That is the
defect class this whole diagnostics corpus exists to make impossible.

**Debug and release fail identically**, which is deliberate and is stated at the site: a
`debug_assert!` here would mean a release build silently drops the registration, i.e. the exact
failure the panic prevents, present in precisely the build where it is hardest to diagnose.

## How to fix

- **Do all configuration before the first `finish()` / `update()` / `run()`.** That is the whole
  rule; the panic names the method you called too late.
- **A runner is not a config phase.** `App::run` hands control to the installed runner *before*
  `finish()`, and the runner calls `finish()` itself - so code that runs from inside the runner is
  already past this line. Registration belongs in a `Plugin::build`.
- **To change behaviour at run time, change data, not the schedule.** `IsEnabled<T>` / `EnableTag`
  turn a registered system on and off structurally, and a resource carries a value the systems
  read. Neither needs the schedule to be edited after it is built.
- **If you genuinely need a system that appears later**, register it up front behind a `run_if`
  condition - the schedule is built once and the condition is evaluated every frame.
