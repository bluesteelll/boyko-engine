# boyko-W0701 — an event lane was full and the send was refused

## What happened

A send into an event buffer found the writing thread's lane at capacity, so the events were
refused rather than written:

```text
boyko-W0701: event buffer full for 'my_game::DamageEvent' on lane 3: 1 attempted, 1 dropped;
             raise EventConfig's capacity_per_lane or drain the reader more often
```

Raised from `crates/boyko_ecs/src/ecs/core/events/event_buffer.rs`, from `send_one` (always
`1 attempted, 1 dropped`) or from `send_many` (all-or-nothing: `n attempted, n dropped`, and
nothing was written).

## Why

Event lanes are fixed-capacity, per-writing-thread, and swapped once per frame. There is no growth
path on the send side by design: a `Vec::push` that may reallocate is exactly what a per-thread
lock-free lane exists to avoid, and reallocating under a `&self` receiver on a worker thread is not
representable at all.

The refusal itself was already reported — `send_one`/`send_many` return
`EcsError::EventBufferFull`, which carries the type name, the lane, and both counts. **Nothing read
it.** The `Result` is discarded at almost every call site, because a gameplay system writing an
event has no recovery to offer, and the per-lane `overflow_count` it also bumps is a number nobody
prints. The condition was therefore fully instrumented and completely invisible, which is why this
code exists: the four fields in the message are the four fields that were already in the error.

**The `Result` is unchanged.** A caller that does check it sees exactly what it saw before.

`RatePolicy::Once`, applied **per call site**: `send_one` and `send_many` latch independently, so
a storm through one does not silence the other. The magnitudes stay in the per-lane
`overflow_count`, which is what a reader compares; repeating the line every frame would bury the
frame that mattered.

## How to fix

- **The capacity is too small for the burst.** Raise `capacity_per_lane` in the `EventConfig`
  passed to `preregister_event::<E>`. Lanes are per writing thread, so the memory cost is
  `thread_count × capacity_per_lane × size_of::<E>()`.
- **The reader is not keeping up.** Events survive one swap. A reader that runs every other frame,
  or that is ordered after the swap in its own frame, sees a lane that never drains. Check the
  reader system's ordering against the dispatcher's swap point.
- **The producer is genuinely unbounded** — one event per entity per frame over a growing
  population. Batch on the producing side, or make the event carry the batch rather than sending
  one per item.
