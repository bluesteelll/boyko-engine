# boyko-W3006 - the render path was degraded

## What happened

The resolved render path is not the one that was asked for:

```text
boyko-W3006: render path degraded (MissingConsumer(VisibilityBuffer))
```

Raised from `crates/boyko_app/src/runner.rs`, once per reason, during boot. The engine renders on
the fallback path.

## Why

`boyko_render::resolve_render_path` takes the requested path, the set of consumers registered for
it, and the device capabilities, and returns what can actually run plus **a set of reasons** it did
not return what was asked. Degrade-not-panic is the rule: a host that cannot serve the requested
path renders on one it can, rather than refusing to start.

**`RatePolicy::Every`, and that is the interesting decision on this row.** The emitter walks a SET:

```rust
for degrade in render_path_degrades.reasons() { warn!(..) }
```

A `Once` latch here would report the first reason and silently drop every other one - the reader
would learn that the path degraded and never learn it degraded twice, for two unrelated causes.
That is `boyko-W2102`'s F11 failure mode reached through iteration instead of through separate call
sites, and it is why this row is the only degrade code in the `30xx` block that is not `Once`. The
comment at the site said "warn-once boot diagnostics" before L8b; it was describing an intent the
loop contradicted.

## How to fix

- **Read the reason, not the code.** The reasons are distinct conditions with distinct repairs; the
  code only tells you the path moved.
- **A missing consumer** means the path was requested but nothing registered to render on it -
  usually a plugin that was not added. This is a wiring problem in the host, not a device one.
- **A missing capability** is a device fact. The paths degrade in a fixed order and the fallback is
  always renderable.
- **To see what was actually resolved**, the boot log line above this one names the path and the
  geometry legs that were selected, and `BOYKO_RENDER_PATH` is the override that requested it.
