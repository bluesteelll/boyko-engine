# boyko-E3011 — a panic escaped an ECS entry point the windowed host owns, and the process aborted

## What happened

A panic reached one of the eight routes the windowed runner uses to enter the ECS. The host caught
it at that boundary, recorded which route it was, flushed the log, and aborted the process:

```text
boyko-E3011: a panic escaped the <stage> ECS entry point (<panic message>) - aborting
```

Raised from `crates/boyko_app/src/diag.rs` (`report_fatal_ecs_panic`), reached from `runner.rs`'s
`guarded` wrappers. `<stage>` is one of `startup`, `sdf-edit-gather`, `asset-upload`,
`vb-geometry-backfill`, `frame`, `vb-instance-ring`.

The panic's own message was printed by the default hook at the origin (and written to the crash
file by the chained hook installed at boot) before the host saw it; the message repeated here is
the payload's `&str`/`String` rendered into a bounded stack buffer, so a very long one is
truncated rather than allocated.

## Why

The three things a windowed crash must do are: stop, say why, and be classifiable. Before this
boundary existed, a panic in a system under the window did none of them — the window stopped
repainting, the process stayed alive with no CPU, and nothing was printed.

**The catch is inside `run_windowed`'s own frame, deliberately.** `WindowHost` and the renderer are
locals of that frame. A catch further out would let the unwind run their `Drop` — device-idle
waits, swapchain teardown — from the state a system had just corrupted, which is exactly what the
shipped crash handlers this design was measured against argue against ("minimal in-process
actions"). So GPU objects are **not** destroyed on this path; validation layers would report leaks
at process death, and that is accepted: the process is dying and the driver reclaims.

**It is not a process-wide panic hook.** A hook fires at the panic's origin and would kill panics
the engine legitimately recovers from — `CommandQueue::apply`'s recovery, the pool's scope capture,
the worker backstop — destroying the propagate-to-owner semantics the rest of the engine is built
on. The existing chained crash-file hook stays as it is: it records, and does not decide.

**`abort()` and not `exit(101)`**, though `101` is what the headless runner produces and agreement
would have been convenient. `ExitProcess` terminates every other thread and then runs
`DLL_PROCESS_DETACH` for each loaded DLL; with the Vulkan loader and an ICD holding a live device
and a killed render thread holding a loader lock, detach is a documented deadlock class — a process
that never exits, window ghosted, no CPU. That is this defect's own symptom moved from the
scheduler to process exit, and a termination mechanism for a hang defect must not be able to hang.
`abort` runs no `atexit` handler, no TLS destructor and no DLL detach.

## Exit status, and what a harness may rely on

**Rely on: non-zero, and promptly.** The numeric value is a property of the host *and of whoever
reads it*, not a design property, and is deliberately not asserted by any test. An earlier revision
of this page shows why: it recorded **127** for the sibling abort "as observed by the test
harness". But the Rust harness observes `0xC0000409` for P8's child, which ends through the same
`std::process::abort()`. `127` was what Git Bash reported. Both numbers were real; they came from
different observers. What the gates assert is `!status.success() && status.code() != Some(0)`.

For calibration, measured on this tree's `stable-x86_64-pc-windows-gnu` toolchain:

| Observer | Process | Observed status |
|---|---|---|
| Rust `std::process::Command` — P8, `diag::tests::a_frame_panic_ends_the_process_visibly` (debug and release) | a child that reaches `report_fatal_ecs_panic` and its `std::process::abort()` | `0xC0000409` (`3221226505`); `code() == Some(-1073740791)` |
| Git Bash `timeout` / `$?` | the same P8 child | `127` |
| Git Bash `timeout` / `$?` | a run ended by the *sibling* abort site (`boyko-E0201` in `detached_spawn_panic_does_not_block_pool_shutdown`; the same `std::process::abort()`, two statements after the same flush) | `127` |
| Git Bash `timeout` | a hung child it killed at its deadline | `124` |

`0xC0000409` is `STATUS_STACK_BUFFER_OVERRUN`, the status the kernel gives a process that ends
through `__fastfail`. That is how `std::process::abort` ends a process on Windows x86_64 under
**both** `gnu` and `msvc` targets: in the standard library this toolchain ships,
`sys/pal/windows`'s `abort_internal` executes `int 0x29` with `FAST_FAIL_FATAL_APP_EXIT`, selected
by architecture alone. So the number does not mean a buffer overrun happened. Git Bash does
not pass the NTSTATUS through, and reports `127` instead.

Classification, without parsing text: a wall-clock kill is the harness's own timeout (`124` under
Git Bash `timeout`); `101` is a panic that escaped `main` in a headless host; a deliberate engine
abort is either the pool's detached-task abort or this one, told apart by the code in the log and
the crash file.

On an interactive desktop, Windows may present an error-reporting dialog before the process ends.
That is expected and is **not** suppressed: `SEM_NOGPFAULTERRORBOX` would also suppress the crash
dump, and a crash we can see is worth more than a dialog nobody has to click. A headless or CI run
never raises one. The same is already true of the pool's abort, so this is not a new class.

Under `panic = "abort"` the process dies at the panic's origin instead, after the hook has printed;
this line is never reached, and the two signatures differ.

## How to fix

The panic is the defect; the abort is the report.

- **Read the panic printed above this line**, and the `boyko-E1502` line if one is present — that
  one names the system.
- **`<stage>` tells you when.** `startup` is `App::finish()` draining startup systems with the
  window already up; `frame` is the per-frame ECS update; the rest are one-shot systems the host
  runs around the frame.
- **If you are embedding this engine and want to survive the panic**, do not use the windowed
  runner's boundary: call `App::update_with_delta` yourself and catch it. You then own the
  post-panic contract documented on `Schedule::run` — the schedule is structurally reusable, the
  world is semantically partial.
