# boyko-E2101 — validation was requested but this process is not getting it

## What happened

A caller asked for Vulkan validation (`InstanceConfig { enable_validation: true, … }`) and the
process is not running with what was asked for. Two arms, one code, because they mean the same
thing to a reader:

```text
boyko-E2101: validation was requested but BOYKO_DISABLE_VALIDATION withheld it; no messenger is
             created and no validation message can be produced -- a clean run proves nothing
```

```text
boyko-E2101: validation is on but VK_EXT_validation_features is absent, so synchronization
             validation is NOT enabled; this run cannot flag a missing or wrong barrier
```

Raised from `crates/boyko_rhi_vulkan/src/device.rs` — the first from `VulkanContext::boot`, before
the loader is touched; the second from `create_instance`, where the extension's presence is probed.
`RatePolicy::Once` per site: the answer is a property of the process, not of the boot, so a host
that creates several contexts is told once.

## Why

**A run that looks validated and is not is worse than a run that is openly unvalidated.** The whole
value of a validation-on run is the inference "no messages, therefore no API misuse" — and that
inference is only sound if the layer was actually there. Both arms break it silently:

- The `BOYKO_DISABLE_VALIDATION` escape hatch exists so the golden image tests can boot on a host
  where the SDK layer is unusable. It is correct and it is used by **every golden leg**. Until this
  code existed, nothing in the output said so, and a reader of a clean golden run had no way to
  know which of the two states produced it.
- `VK_EXT_validation_features` carries the chained `VkValidationFeaturesEXT` node that turns on
  **synchronization** validation — the part that flags a missing or wrong pipeline barrier. Without
  the extension the node is not recognised and the run silently downgrades to plain validation,
  which checks API usage and says nothing about barriers.

It is an `error!` rather than a `warn!` because the caller asked for something and did not get it —
the engine could not do what was asked.

## How to fix

Decide which state you want, and note that both are legitimate:

- **You want validation.** Unset `BOYKO_DISABLE_VALIDATION`, and install the Vulkan SDK if the
  second arm fired (it supplies `VK_EXT_validation_features` along with the layer).
- **You do not want it here** — a golden run, a benchmark, a machine where the layer is unusable.
  Then this line is the record that the run was unvalidated, and it is doing its job. Do not read a
  clean run from such a process as evidence about API usage or barriers.
- **You did not mean to ask.** Set `enable_validation: false` in the `InstanceConfig`; that
  short-circuits the environment read entirely and nothing is withheld, so this code cannot fire.

**What this code cannot tell you**, and the reason matters: that a *present* layer is a *sensitive*
one. `crates/boyko_rhi_vulkan/tests/compute.rs::negative_chained_barrier_hazard` documents in this
repository that synchronization validation is enabled on this hardware and still does not flag a
compute→compute read-after-write hazard. The engine can observe whether the instrument was
installed; it cannot observe what the instrument fails to notice. A bit-exact golden remains the
load-bearing oracle for that class.
