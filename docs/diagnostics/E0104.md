# boyko-E0104 - two downstream log targets claim one id

## What happened

Two `define_target!` declarations picked the same id in the downstream band, and both registered:

```text
boyko-E0104: downstream target id 96 is claimed by combat and cannot also be inventory
```

Raised from `crates/boyko_log/src/target.rs`. The **first** registrar keeps the id; the second's
`register()` returns `false`. Nothing crashes, and the loser's records still emit — onto the
*winner's* control byte, which is exactly why this is an error and not a warning: two categories
share one runtime level, so turning one on turns both on.

## Why

The engine's own targets cannot collide — `targets!` is one table with a strictly-increasing `const`
assert, so a duplicate does not compile. The downstream band has no such table by design: two crates
that never see each other must be able to declare targets without coordinating through this
repository.

**Both colliders are named, and that is why the claim table stores names rather than bits.** A
bitmap would report "id 96 is taken" and leave a reader grepping two crates by hand. The report that
does not say who took it is the report the diagnostic code was invented to replace.

`RatePolicy::Every`. A binary with three colliding pairs has three different things to say, and a
latch would name one of them — the same argument `W0901` records for component types and `E0106` for
refused names.

**An out-of-band id is a different failure and is caught earlier.** `TargetId::new_downstream`
carries a `const` assert for `96..=223`, so `id = 300` **does not compile**. Only same-band
collisions can reach run time, which is what Decision 15 means by ids being valid by construction.

**Re-registering the same name is not a collision.** A registrar reached from two entry points is
not a design error, so `claim_downstream` compares names and stays silent when they match.

## How to fix

- **Pick a different id.** The band is `96..=223` — 128 ids, shared by every downstream crate in the
  build.
- **Read both names in the message.** They tell you which two declarations to reconcile; the id
  alone does not.
- **Register at boot and check the return.** `register()` returns `false` on collision, so a host
  that would rather refuse to start than run with two categories sharing a control byte can.
- **If you need many categories from data rather than from source**, the dynamic band is the right
  tool: `register_dynamic_target` interns by *name* and cannot collide, at the cost of gate (a).
