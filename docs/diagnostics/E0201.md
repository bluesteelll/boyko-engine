# boyko-E0201 — a fire-and-forget task panicked and the process aborted

## What happened

A closure handed to `ThreadPool::spawn` — or picked up by the dispatcher's work-stealing join —
panicked. The pool caught the unwind, reported it, and aborted the process:

```text
boyko-E0201: a fire-and-forget task (ThreadPool::spawn) panicked; aborting the process
             (no joiner can receive the payload)
```

Raised from `crates/boyko_threadpool/src/worker.rs` (`abort_on_task_panic`), reached from
`run_task`'s `catch_unwind`. The **panic's own message** was already printed by the default panic
hook, which runs at the unwind's origin, before the unwind reaches this catch. This line records
the *decision*, not the cause; read the line above it.

## Why

`spawn` is fire-and-forget: nothing joins the task, so there is no caller to hand a payload to. The
two alternatives are both worse.

Letting the unwind escape would tear down the worker thread and shrink the pool to `n-1` threads
for the rest of the process — a silent, unrecoverable degradation that shows up much later as a
throughput mystery. Swallowing the panic would leave whatever invariant the task was in the middle
of establishing half-established, with nothing recording that it happened.

The same discipline covers the dispatcher's join (`Scope::drop` →
`join_workers_until_drained`), which steals from the same deques a worker does and can therefore
pick up a fire-and-forget task. An unwind escaping *there* would abandon the join — and that join is
the entire justification for the `'scope → 'static` transmute, so the caller's frame and every
stack borrow the still-running tasks hold would be popped out from under them: a use-after-free
reachable from safe code.

Aborting matches rayon's documented `spawn` behaviour, and is chosen for the same reason.

## How to fix

The panic is the defect; the abort is the report.

- **Fix the task.** Find the panic message printed immediately above this line and treat it as any
  other panic.
- **If the task can legitimately fail, make it say so.** Use a joined `ThreadPool::scope` task and
  return a `Result`, or catch the failure inside the closure and record it. A task that may fail is
  not a fire-and-forget task.

A note on **what you will and will not see**: the pool `flush()`es the log before aborting, because
`abort` runs no destructor and no `atexit` handler, so a record still sitting in its lane ring at
that instant is lost with the process. If diagnostics were never enabled, `flush` reports
`NoConsumer` and the pool writes the line to `stderr` itself — that is the only configuration in
which it writes for itself, and it is the configuration in which nothing else would.
