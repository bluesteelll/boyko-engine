# boyko-E0109 - the crash file could not be opened

## What happened

Diagnostics were enabled and the crash destination could not be created:

```text
boyko-E0109: the crash file /var/log/boyko-crash.log could not be opened; a panic in this process will leave no record
```

The process continues. Every other sink is unaffected. What is gone is the artifact a panic would
otherwise have left.

## Why it is reported HERE and not during the panic

A panic hook runs on a thread that is already unwinding - possibly out of stack, possibly holding
the very allocator lock the panic came from. Opening a file there is the most likely single way to
turn a diagnosable crash into a silent one. So the handle is created **when diagnostics are turned
on**, still before the first frame, and the hook only writes to something that already exists.

That timing is what makes this report useful: it arrives while there is still a healthy process to
receive it, rather than being discovered at the one moment nothing can be reported at all.

`Once` - one process has one crash destination, and a second attempt fails for the same reason.

## How to fix

- **Check the directory exists and is writable** by the account running the process. This is the
  usual cause, and it is usually a deployment difference rather than a code one.
- **Check the path**: `arm()` takes it verbatim; a relative path resolves against the working
  directory, which for a service is often not where anyone expects.
- **Check for a stale handle**: on Windows a file another process holds open cannot be replaced.
- **Or accept it**: if this build genuinely has no crash destination, the report is telling the
  truth and the fix is to stop arming one.
