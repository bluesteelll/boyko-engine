# boyko-W9214 — the telemetry path is unwritable, so this session streams nothing

## What happened

The profiler was armed with a telemetry configuration, and the file that configuration names could
not be opened for writing:

```text
boyko-W9214: the telemetry path could not be opened; this session streams nothing
```

Raised from `crates/boyko_app/src/profiling/stream.rs` (`Stream::open`) through
`boyko_diag::loss::DiagFlag::TelemetryPathUnwritable`, and emitted by
`crates/boyko_ecs/src/ecs/core/profiling/diag.rs` (`report_telemetry_path_unwritable`) at the next
fold — the substrate is diagnostically mute, so a condition it observes reaches a reader through the
profiler's own emitter.

Everything else about the session is unaffected. The in-memory ring, the retention tiers and every
`Res<Profiler>` reader work exactly as they would without a telemetry config; what is missing is the
durable file.

## Why it fires on the ENABLE path and not at process start

**The telemetry file is opened by `arm`, never by the process.** A run that never arms the profiler
opens no file, touches neither page of the double buffer, and cannot raise this code. That is what
makes "profiling off costs nothing" a structural claim rather than a measured one — there is no path
from process start to this open.

The corollary is the one worth remembering: **a build that never emits `W9214` is not a build with a
writable path.** It is, far more often, a build that never armed.

## What causes it

- The directory does not exist. The writer does not create one: a telemetry path is chosen by
  whoever configured the session, and silently creating a tree somewhere unexpected is worse than
  refusing.
- No write permission, or the file exists and is read-only.
- The path names a directory rather than a file.
- On Windows, another process holds the file open without sharing.

## Why it is a warning and not an error

Nothing is broken and nothing is lost that the process ever had. The session runs; it simply has no
stream. An error would say a measurement failed, and none did.

## Why it fires once

`RatePolicy::Once`. The open is attempted once per arm, so a session produces at most one of these
anyway; the latch is what keeps a process that arms and disarms repeatedly from turning a
configuration mistake into a log flood.

## How to fix

- Create the directory that holds the path before arming.
- Check the permissions on it.
- If the path is chosen from an environment variable, print it — a variable that is set to an empty
  string is a very common shape of this failure and reads as a path that "looks fine".
