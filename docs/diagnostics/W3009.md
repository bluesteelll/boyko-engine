# boyko-W3009 - an unrecognised environment override value

## What happened

A `BOYKO_*` override was set to something this build does not know, and the default was used:

```text
boyko-W3009: BOYKO_RENDER_PATH='forwardplu' unrecognized -> Deferred (valid:
deferred|forward|forwardplus|vb)
```

Raised from `crates/boyko_app/src/plugins.rs`. Two sites - `BOYKO_RENDER_PATH` and
`BOYKO_GEOMETRY_LEGS` - and each record names its own variable, its own rejected value and its own
admitted set.

## Why

The engine has 28-odd `BOYKO_*` switches and no argv parser, so a typo in one is the commonest way
to run an experiment against the wrong arm. Falling back to the default is right - refusing to boot
over a misspelled knob would be worse - but doing it *silently* is how a bench run reads as "no
win, no regression" when it was in fact a self-comparison.

That is the same argument the `VB-P1e` boot line was added for: **every run names the arm it
actually selected**, so a mis-set knob is visible after the fact instead of being inferred from a
null result weeks later.

`RatePolicy::Once`, per site. Each variable is parsed once at boot; the two latches are separate so
a wrong `BOYKO_RENDER_PATH` cannot silence a wrong `BOYKO_GEOMETRY_LEGS`.

## How to fix

- **Read the admitted set in the record.** It is printed verbatim from the parser's own match arms,
  so it cannot drift from what the build accepts.
- **The values are case-insensitive and trimmed**, so a stray space is not the cause; a wrong
  spelling is.
- **`forwardplus` has three spellings** (`forward+`, `forward_plus`, `clustered`) and `vb` has four
  (`visibilitybuffer`, `visibility_buffer`, `visbuffer`). If one you expected is missing, it is not
  in the match.
- **Confirm what was actually selected** on the `render-path override from env` line that follows -
  it names the resolved path and legs, and it is the line worth pasting into a bench report.
