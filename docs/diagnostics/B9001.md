# boyko-B9001 — the schedule contains a cycle of systems

## What happened

The ordering constraints given to a `ScheduleBuilder` cannot all be satisfied: following them leads
back to where it started.

```text
boyko-B9001: schedule contains a cycle of 3 systems: ["apply_damage", "spawn_effects", "apply_damage"]
```

Raised from `crates/boyko_ecs/src/ecs/core/schedule/schedule_builder.rs`
(`ScheduleBuildError::OrderingCycle`). `ScheduleBuilder::build` panics with it;
`ScheduleBuilder::try_build` returns it as an `Err` for a tool or library caller that wants to
surface the failure instead.

## Why

A schedule is a DAG. The parallel executor's whole model is "a system may start when every system
with an edge into it has finished", and a cycle makes that condition unsatisfiable for every system
on it — the executor would either deadlock or, worse, run them in whatever order the topological
sort happened to abandon.

Detection is at **build** time, once, rather than at run time, and the cycle is reported with the
**names on it** rather than as a count. The names are what locate the constraint: a cycle is
almost never written down as a cycle, it is assembled from two or three `.before`/`.after` calls in
different files, and a message naming only the length would leave an author reading all of them.

Note that the printed list closes the loop — the first name appears again at the end — so it reads
as a path rather than as a set.

## How to fix

Follow the printed path and find the edge that should not be there. One of them is wrong, and the
usual shapes are:

- **A `.before` and an `.after` that say the same thing backwards.** `A.before(B)` in one file and
  `B.before(A)` in another are each individually reasonable.
- **A set edge that expanded wider than intended.** `A.before(SomeSet)` adds an edge to *every*
  member of the set, including ones added later by a plugin. If a member of `SomeSet` is already
  ordered before `A`, the cycle appears when the plugin is added and not before.
- **A genuine mutual dependency.** Two systems each need the other's output. That is not an
  ordering problem: split one of them, or move the shared step into a third system both are
  ordered after.

If the two systems do not actually constrain each other, delete the edge rather than reversing it —
an unnecessary ordering edge costs parallelism whether or not it forms a cycle.
