# boyko-W9210 — a game's zone budget is exhausted

## What happened

A `User`-partition crate asked for a zone id past `MAX_USER_BUDGET`, or `register_zone` found the
dynamic name arena full:

```text
boyko-W9210: the user zone budget or name arena is exhausted at 3072 of 3072 slots;
             further game zones run unregistered
```

Raised inside `boyko_diag::profiling_abi::mint_id_in` (the `User` arm) and inside
`register_zone`'s name-arena check, as `DiagFlag::UserZoneBudgetExhausted`; emitted from
`crates/boyko_ecs/src/ecs/core/profiling/diag.rs` (`report_user_budget_exhausted`).

## Why this is not `boyko-W9201`

They are the same *shape* of event with different owners, and telling them apart is the whole reason
there are two codes.

`boyko-W9201` says the **engine** ran out of the slots it reserved for itself. A host cannot act on
it: it does not choose `ENGINE_ZONE_SLOTS`, and the fix is an engine change.

`boyko-W9210` says a **game** met a budget the **host** chose. That number *is* the host's — it is
`MAX_USER_BUDGET` at build time and `ProfilerConfig::user_zone_budget` at arm — so this code has
advice attached and its sibling does not. Reporting both as one would hand a host the wrong one half
the time.

## Both authoring paths spend the same budget

A game's static `declare_zone!` and its dynamic `register_zone` draw from **one** counter. That is
deliberate (the corpus's D19): from the id space's point of view they are the same traffic, and
keying the partition on the macro instead puts the recommended game path inside the isolation the
design exists to provide. So a plugin that registers 3 000 zones from a manifest leaves 72 for every
static zone in the title.

## Nothing is lost except names

The zone still runs. Its interval still accumulates on its own handle; what is missing is the
registry entry, so its samples carry an id no reader can resolve to a name. The refusal is counted
(`LossClass::Refused`) rather than thrown — a profiler that aborts a shipped title because a mod's
manifest had one zone too many has become the failure it exists to report.

**The engine is unaffected.** The two id ranges have separate counters, so a game exhausting its
budget cannot consume an id the engine was going to use. That property is gated
(`crates/boyko_diag/tests/profiling_user_id_space.rs`), and its RED is a game's static zone minting
an engine id.

## How to fix

- **Register fewer zones.** The usual cause is a per-*instance* registration where a per-*type* one
  was meant: one zone named `"mob.goblin.tick"`, not one per goblin. A `DynZoneHandle` is 16 bytes
  of `Copy` data precisely so it can be minted once and stored wherever the instances are.
- **Raise `user_zone_budget`** in `ProfilerConfig` if the count is legitimate. It sizes the store's
  columns, so it costs `WINDOW × 21 B` per extra zone in the reservation.
- **Raise `MAX_USER_BUDGET`** only if the budget itself is too low to configure around. It sizes two
  `.bss` arenas and the upper half of `REGISTRY` — 32 bytes per id — and it is bounded: zone ids are
  `u16`, so `ENGINE_ZONE_SLOTS + MAX_USER_BUDGET` must stay under 65 535.
- **If the message says the NAME arena rather than the slots**, the cause is name *text*, not zone
  count. `DYN_NAME_BYTES` is one shared arena with no per-zone cap, so a single very long generated
  name can starve later registrants. Shorten the names before growing the arena.
