# boyko-E2203 - a GPU dispatch failed inside a system that has no error channel

## What happened

`GpuSystem::run_unsafe` recorded and submitted a compute dispatch and the RHI refused it:

```text
boyko-E2203: GpuSystem dispatch failed: <the GpuColumnError's own text>
```

Raised from `crates/boyko_render/src/gpu_system.rs`. In a debug build the `debug_assert!` beside
the report fires first and the process dies at the fault. In release the frame continues: the
dispatch simply did not happen, so whatever the GPU-resident column was supposed to compute this
frame holds its previous contents.

## Why

The `System` trait's `run_unsafe` returns `()`. There is no `Result` to propagate, and a GPU system
runs solo on the dispatcher thread inside the apply window, so there is no caller positioned to
handle a failure either. That is the whole reason this code exists: **the logger is a side channel
available from any thread**, and it is the only way this condition reaches anybody.

`RatePolicy::Every`, and the flood is deliberate. A device fault that recurs every frame can only
reach an operator as a record per frame; a `Once` here would report the first bad frame of a session
and then let an hour of broken frames look identical to a good one. The flood is bounded by the
ring, which drops and counts under pressure - **not** by the registry's rate column, which the
emission macros do not read (see `RatePolicy`'s own doc for that measurement).

Class `E` rather than `W` because the engine was asked to do something and could not.

## How to fix

Read the embedded `GpuColumnError` first - it names which stage refused:

- **A resolve failure** (`(archetype, component)` did not resolve to a live device column) usually
  means the column was never minted, or an archetype move retired it. Check that the component is
  registered as GPU-resident and that the entity actually carries it.
- **A submit or fence failure** is a device error. Run with validation on
  (`BOYKO_DISABLE_VALIDATION` unset) and look for the layer's own diagnosis immediately before this
  line; it will be far more specific than this code can be.
- **A device loss** makes every subsequent frame produce this line. That is the intended behaviour -
  the repetition is the signal that the device did not recover.
