# boyko-E1503 — the completion queue overflowed while publishing a system, and the process aborted

## What happened

A system's run guard tried to publish its completion on the **unwinding** path and the completion
queue refused the push. The schedule recorded the fact, flushed the log, and aborted:

```text
boyko-E1503: completion_queue overflowed publishing system #<index>; aborting
```

Raised from `crates/boyko_ecs/src/ecs/core/schedule/schedule.rs` (`completion_queue_overflow`),
reached only from `SystemRunGuard`'s `Drop`.

## Why

This site is **unreachable by construction**, and it exists so that if the construction ever
changes the process says which invariant broke instead of hanging.

The capacity proof has three parts: the queue is `ArrayQueue::new(system_count.max(1))`, a guard
publishes exactly once per system per frame (SP2 — `finish` publishes and disarms, `Drop` returns
early when disarmed), and SCH6 proves the queue empty between frames. If a push is refused, one of
those three is false.

Aborting is chosen against the two alternatives, both of which are worse **here specifically**:

* the normal path's `.expect(…)` would, inside a cleanup pad, become
  `panic in a destructor during cleanup` — an abort that names the destructor rather than the
  invariant, and reaches the reader with no code to look up;
* dropping the completion silently would be **defect A6 itself**: the dispatcher waits for a
  completion that never arrives, the apply window never opens, and the process hangs with no CPU
  and no message. That is the defect this whole guard exists to remove.

The `stderr` fallback is not decoration. With `BOYKO_LOG` unset — the default for every run that
is not itself a logging experiment — every target's ceiling is `Off`, so the record above is never
*constructed*; and `abort` is not an unwind, so there is no panic text either. Without the
fallback, the one configuration in which this site can fire is the one in which it would say
nothing. `crates/boyko_log/tests/print_allowlist.txt` carries the row that permits the print, and
the census asserts that ledger in both directions.

## How to fix

This is an engine defect, not a user error. If you see it:

- **Report it with the system index and the preceding panic**, which is the state the guard was
  unwinding from.
- **Check whether anything publishes a completion twice** — a second `finish`/`Drop` publish for
  one system per frame is the only way the capacity proof fails at a realistic system count.
- **Check `reset_for_frame`.** If a previous run left entries in the queue, the next run starts
  against a partly full queue; the `SCH6` debug asserts fire first in a debug build, which is why
  this line is normally reached only in release.
