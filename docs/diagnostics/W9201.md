# boyko-W9201 — the engine zone registry is exhausted

## What happened

A zone asked the engine registry for a slot and there were none left:

```text
boyko-W9201: the engine zone registry is exhausted at 4096 slots; further zones run unregistered
```

Raised inside `boyko_diag::profiling_abi::mint_id` as `DiagFlag::ZoneRegistryExhausted` plus a
`LossClass::Refused` count, and emitted from
`crates/boyko_ecs/src/ecs/core/profiling/diag.rs` (`report_registry_exhausted`) at the next fold —
the substrate is diagnostically mute, so a condition it observes reaches a reader through the
profiling fold or not at all.

## What "unregistered" actually costs

The zone still **runs**. Its guard still opens, still closes, still measures. What it does not get
is a registry slot, which means:

- Its samples carry `ZONE_ID_EXHAUSTED`, so the fold has no column to accumulate them into.
- No reader can resolve that id to a name.

So it is a **missing measurement**, not a wrong one. Nothing else in the window shifts, and no
figure becomes false because a zone went unregistered.

## Why it is not terminal, which is a deliberate reversal

An earlier revision mirrored `query_type_registry.rs`'s terminal exhaustion. That precedent does
not transfer, and the difference is the whole reason:

- A **query-shape** registry answers a *semantic* question. A missing entry there is a **wrong
  answer**, and failing loudly is right.
- A **zone** registry answers a *measurement* question. A missing entry is a **missing
  measurement**, and taking the process down over one is the instrument becoming the failure.

The arithmetic makes the terminal form actively dangerous. An `App` runs at least `Startup` +
`Fixed` + `Main`, the cap is `MAX_SYSTEMS_PER_SCHEDULE = 1024` per schedule, and per-system minting
is unconditional at the `Deep` tier — so a legal app that never asked to profile anything could
have panicked at build time.

## Where the slots go

`ENGINE_ZONE_SLOTS = 4096`, shared by:

- every static `declare_zone!` site in every engine crate, minted on first use;
- **one per system per schedule**, minted at `ScheduleBuilder::try_build` when the compile tier
  admits system zones (`Deep`);
- a small number abandoned by threads that raced on a zone's very first use — bounded by zones ×
  racing threads, and each costs one slot.

**A game's zones are NOT in that list, and before profiling rung 10 they were.** Until the id space
was split there was one counter for both partitions, so a `profiling_partition!(User)` crate's
static `declare_zone!` minted an engine id — meaning a plugin with three thousand zones could
produce this code, and this page would have sent whoever read it looking through engine crates for
the cause. `ENGINE_ID_NEXT` and `USER_ID_NEXT` are now separate counters over disjoint ranges: a
game meeting its own ceiling raises `boyko-W9210`, never this one. So if you are seeing `W9201`, the
demand is genuinely the engine's.

## Why it fires once

`RatePolicy::Once`, with a site-local latch. Every later mint fails the same way; the count lives
in the substrate's `Refused` cell, which keeps climbing after the code has gone quiet.

## How to fix

- **Build at a lower tier.** `Deep` is what puts a zone on every system; at `Dev` or `Always` the
  minting loop is deleted from the build entirely and four thousand slots go back to static zones.
- **Split the schedule.** The systems are the bulk of the demand, and a thousand systems in one
  schedule is a lot of systems.
- **Raise `ENGINE_ZONE_SLOTS`.** It is a per-profile constant. The cost is `REGISTRY` (8 B/slot)
  plus the column stride, which is `21 B × zone_stride × 121` — the second term is the expensive
  one, and crossing the L1d threshold gets its own code (`boyko-W9211`).
