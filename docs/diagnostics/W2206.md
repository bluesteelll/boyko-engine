# boyko-W2206 - a material texture file exists but failed to decode

## What happened

`load_material_folder` found a candidate file for one of the material's texture slots, read it, and
the PNG decoder refused it:

```text
boyko-W2206: load_material_folder: albedo at assets/materials/rock/pbr/albedo.png failed to decode
(<the PngError's own text>), using the material fallback
```

Raised from `crates/boyko_render/src/texture.rs`. The slot resolves to bindless slot `0` - the
material's scalar/vertex-colour fallback for that channel - and the load continues. The material
renders; that one map does not contribute.

## Why

Every one of the five folder slots is documented as optional, so a **missing** file is the normal
case and gets an `info!` with no code at all. Warning on absence would put a `Warn` in the log of
every material that ships four maps instead of five, which trains a reader to ignore the level.

A file that is *present* is different: somebody put it there intending it to be used, and it
silently is not. That asymmetry is the whole reason this code exists and why its sibling arm does
not have one.

`RatePolicy::Once`, per site: a broken asset pipeline produces the same failure for every material
in the pack, and the first one is the one worth reading.

### A known limit, recorded rather than papered over

The missing-file arm also covers an **unreadable** file, because `resolve_candidate` discards the
`io::Error` with `.ok()`. A permissions fault on `albedo.png` is therefore reported at `info` level,
alongside a genuinely absent optional map. Splitting the two means returning the reason from
`resolve_candidate` and re-blessing the three tests that pin its `Option` signature; it is filed in
`docs/OPEN-QUESTIONS.md` with that cost rather than folded silently into the migration rung.

## How to fix

The embedded `PngError` names the specific refusal:

- **`Signature`** - the file is not a PNG. A `.jpg` or a Git LFS pointer renamed to `.png` is the
  usual cause, and both are common in asset packs.
- **A palette or interlace rejection** - this decoder supports colour types 0/2/4/6, bit depths 8
  and 16, non-interlaced. Re-export without Adam7 interlacing and without a palette.
- **`Truncated` or a DEFLATE error** - the file is damaged. Re-download or re-export it; note that
  a *checksum* mismatch alone would not reach this code, because the decoder continues past those
  and reports `boyko-W2601` / `boyko-W2602` instead.
- **`DimensionOverflow`** - the header claims more than 256 MiB of decoded pixels. For a real
  texture this means a corrupt `IHDR`, not a genuinely huge image.
