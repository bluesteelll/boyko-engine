# boyko-W2102 — a device format feature is missing, so a render feature is disabled

## What happened

A `vkGetPhysicalDeviceFormatProperties` probe at boot found that this GPU does not advertise
`STORAGE_IMAGE` on a format one of the optional render features needs, so that feature was turned
off for the whole process. Three independent probes share this code:

```text
boyko-W2102: DDGI disabled: B10G11R11/RG16F storage unsupported (irr_ok=false, depth_ok=false)
boyko-W2102: shadow denoise disabled: RG16 UNORM storage unsupported (rg16_ok=false, rg8_ok=true)
boyko-W2102: SSAO a-trous denoise disabled: R16 UNORM storage unsupported
```

Raised from `crates/boyko_rhi_vulkan/src/device.rs`, all three inside `query_device_caps`. **None of
them fails the boot** — every one of the three subjects is opt-in, and the engine is designed to run
without it: the DDGI resolve clamp and the no-storage atlas fallback cover the first, the
target-allocation gate covers the second, and the third degrades to the raw un-denoised gather.

## Why

**A degrade-to-disabled that nobody is told about is indistinguishable from the feature being
broken.** Someone enables DDGI, sees no indirect light, and has no way to learn whether the probe
update is wrong or was never allowed to run.

Two properties of this code are deliberate and worth knowing:

- **It is not `#[cfg(debug_assertions)]`.** All three of these were debug-only `eprintln!` before
  rung L7b, which means the *shipping* build — the one an operator actually runs — turned a render
  feature off in silence. `crates/boyko_app/src/host.rs` had already written the opposite rule for
  its own degradation ("Emitted UNCONDITIONALLY (not `#[cfg(debug_assertions)]`): a RELEASE-build
  degrade-to-Off must be observable"); L7b settled the conflict that way for these three too.
- **The `Once` latch is per SITE, not per code.** A code-scoped latch would have reported whichever
  of the three fired first and dropped the other two — uncounted, because `Once` deliberately does
  not count its suppressions. A device missing all three formats produces three lines. This is the
  case `logging/emission-path`'s F11 was raised for, and
  `device.rs::tests::w2102_reports_every_degradation_not_just_the_first` is the test that holds it.

It is a `warn!` rather than an `error!` because the engine did exactly what it was designed to do:
nothing was asked for and refused, and the frame still renders.

## How to fix

Usually nothing — this is a report about the hardware, not about a defect:

- **You do not use the feature.** Then the line is informational and can be filtered with
  `BOYKO_LOG=error`, or by lowering the `RhiVulkan` target's ceiling.
- **You do want it.** Check the driver first: these are common formats, and an old or fallback
  driver (a basic display adapter, a stale WHQL package, a software rasterizer) is a far more
  likely explanation than the GPU genuinely lacking `R16_UNORM` storage. `vulkaninfo` prints the
  same `optimalTilingFeatures` bits the probe reads.
- **You are reading a benchmark or a golden run from a machine that printed this.** Do not compare
  its numbers against a run that had the feature: a disabled denoise is both faster and different,
  and the artifact does not otherwise record which of the two it measured.
