# boyko-B9005 — ordering references a system key that is not in this schedule

## What happened

A schedule build found an ordering constraint naming a `SystemKey` the schedule does not contain:

```text
boyko-B9005: ordering references SystemKey(N) which is not in this schedule
             (it has M systems); the key is foreign or stale
```

Raised from `crates/boyko_ecs/src/ecs/core/schedule/schedule_builder.rs`
(`ScheduleBuildError::UnknownSystemKey`).

## Why

`SystemKey` is an index into **one** schedule's system list. It is not a global identifier, and
nothing in its type says which schedule it belongs to. Two ways to hold a key the builder cannot
resolve:

- **Foreign** — the key came from a different schedule. Index 7 exists in both, and means two
  different systems.
- **Stale** — the key was taken before the schedule was rebuilt, and the system it named is gone or
  has moved.

Both are caught at build time rather than at run time, and both are caught by *bounds* rather than
by identity: the builder can see that the key is outside its own list, which is why the message can
report `M` systems but cannot tell you which schedule the key came from. That limit is stated here
so a reader does not spend time looking for a "source schedule" field that does not exist.

## How to fix

- **Order by name, not by key.** Ordering constraints expressed against system sets or labels are
  re-resolved on every build and cannot go stale.
- **If you are holding keys deliberately**, re-acquire them after every rebuild, from the same
  schedule you will apply them to. A key does not survive a rebuild and does not travel between
  schedules.
- **Check the count.** The message prints how many systems the schedule has. A key far above that
  number is almost always foreign; a key just above it is almost always stale.
