# boyko-E1502 — a system panicked and the rest of the schedule run was cancelled

## What happened

A system body raised a panic on a worker thread. The executor stopped dispatching, accounted for
every system already in flight, recorded this line, and let the panic propagate to the thread that
called `Schedule::run`:

```text
boyko-E1502: system '<name>' (#<index>) panicked; the rest of the schedule run was cancelled
```

Raised from `crates/boyko_ecs/src/ecs/core/schedule/schedule.rs` (`cancel_after_panic`). The
panic's own message was printed by the default hook at the origin, on the worker; this line says
what the **schedule** did about it.

After this line, `Schedule::run` re-raises the original payload on its caller. A caller that
catches it gets a schedule, a world and a pool that are all structurally reusable — see *How to
fix*.

## Why

Cancelling rather than finishing the run is a decision, and it is the one every cancellable task
system in the survey takes (oneTBB: *"the algorithm is cancelled; pending iterations are not
executed"*; Taskflow skips the throwing task's dependents). The panicked system left the world
**semantically partial**: its successors' preconditions are exactly what it failed to establish.
Running the remaining systems over that state delays the diagnostic and multiplies the damage,
which is the complaint behind bevy#8152's cascade.

Cancellation is at **round** granularity, not task granularity. A system already dispatched runs
to completion, because a registered pool task must always complete its registration — a check
inside the body would abandon one and hang the join.

The record is emitted **after** the drain, not at the moment the flag is claimed, because reading
the panicking system's name walks the systems buffer, and that is race-free only once every
dispatched worker has published and been popped.

`#` is the system's index in the built schedule's topological order. It comes from the cancel flag,
which is first-wins; the payload the caller receives is first-wins too, but through the pool's own
slot. Under a race between two panicking systems the two can name different systems — both are
"first wins, non-deterministic which", which is rayon's documented contract, and it is why the name
here is a strong hint rather than a proof of origin.

## How to fix

The panic is the defect; the cancellation is the containment.

- **Read the panic printed above this line** — the system named here is where it happened.
- **Do not treat a caught `Schedule::run` panic as a recoverable frame.** What the engine promises
  is structural reusability, not that the frame happened: the run's queued commands stay queued in
  the buffer of the system that queued them and are applied the next time that system is applied,
  which happens only in a later run that dispatches it — a system whose run condition is false on
  the next run is skipped without an apply, so its commands keep waiting. The panicked system's
  successors did not run, and the panicked system has already advanced its change-detection window.
- **Entity ids claimed by that run's `Commands` stay claimed** until those commands are applied by
  a later run that dispatches the queuing system — one run's spawns per system, unless the runs that
  dispatch it keep being cancelled before its apply, and released for good only if such a run
  happens.
- Under the windowed host you will not see a caught panic at all: the host ends the process at the
  frame boundary with `boyko-E3011`.
