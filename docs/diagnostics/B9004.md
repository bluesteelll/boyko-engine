# boyko-B9004 — two ordered sets share a member

## What happened

A schedule build was asked to order set `a` relative to set `b` — `a.before(b)` or `b.after(a)` —
while some system belongs to **both** sets. The builder refused, at build time, before the schedule
could run:

```text
boyko-B9004: sets 'a' and 'b' are ordered relative to each other but share member 'S'
             (a system cannot run both before and after itself)
```

Raised from `crates/boyko_ecs/src/ecs/core/schedule/schedule_builder.rs`
(`ScheduleBuildError::SetsOrderedButIntersect`).

## Why

Set ordering is expanded into per-system edges: `a.before(b)` becomes an edge from every member of
`a` to every member of `b`. A system in both sets therefore receives an edge **to itself**, and
"run before yourself" has no schedule that satisfies it.

The builder could have reported this later, as a cycle — the system would appear in a
one-element cycle and surface as `boyko-B9001`. It does not, deliberately: a cycle
report names the *symptom* and leaves the author looking for a `before`/`after` pair they never
wrote, because they wrote a **set** pair. Naming the two sets and the shared member points at the
line that has to change.

## How to fix

Pick whichever is true of your intent:

- **The membership is wrong.** The shared system belongs in one set, not both. Remove it from the
  other.
- **The ordering is wrong.** The two sets genuinely overlap and are not orderable as wholes. Order
  the *systems* that need ordering, not the sets.
- **The sets should be nested.** If every member of `a` is meant to be a member of `b`, say so with
  set nesting rather than with an ordering edge; a subset does not run before its superset.

There is no way to suppress this and run anyway, and that is intentional: the alternative is a
schedule whose execution order depends on which edge the topological sort happened to visit first.
