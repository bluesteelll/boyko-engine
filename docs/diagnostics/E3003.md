# boyko-E3003 - a terminal device error in the frame loop

## What happened

The frame loop asked the device for something it could not deliver, and the run is over:

```text
boyko-E3003: terminal device error at frame fence wait (<the error>) - exiting
```

Raised from `crates/boyko_app/src/diag.rs`, called from the windowed frame loop. `site` is either
`frame fence wait` (the per-slot fence that makes the mapped writes race-free) or `render` (the
post-acquire submit/present chain).

## Why

Both sites are terminal by contract rather than by choice. `frame_driver`'s rule is that the
renderer **must not be reused** after a post-acquire failure: the swapchain image has been
acquired, the semaphore is signalled, and there is no defined way to unwind that without a device
reset. A fence wait that fails means the device stopped answering at all.

Neither is a swapchain-out-of-date, which is *not* an error here - a resize recreates the
swapchain and the blit clamps, on the `Ok` arm one line above.

**One code for two sites.** The distinction the reader needs is *when* the device stopped -
before this frame's work was submitted, or after - which is what `site` carries; the repair is the
same either way.

**This site also writes to `stderr` when there is no consumer** - see `boyko-E3002` for the
measurement and the reason.

`RatePolicy::Every`. The loop returns immediately after, so there is no second occurrence to damp.

## How to fix

- **Look for a device loss.** `VK_ERROR_DEVICE_LOST` with no other explanation almost always means
  a GPU hang: a shader with an unbounded loop, a dispatch far past its intended size, or a driver
  timeout (TDR on Windows). The carried error names the Vulkan result.
- **Re-run with validation on** (`BOYKO_ENABLE_VALIDATION=1`). A hang usually has a validation
  error minutes earlier in the same run; this record is the symptom, not the cause.
- **`VK_ERROR_OUT_OF_DEVICE_MEMORY` here is a different problem** - the frame's allocations
  succeeded at boot, so an exhaustion at this point means something else on the machine took the
  memory. Check for a second GPU consumer.
- **A driver update is a real fix** and is worth trying before instrumenting: this class of error
  is frequently a driver bug on a specific extension path.
