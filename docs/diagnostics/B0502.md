# boyko-B0502 — the query-type table is exhausted

## What happened

A distinct `Query<D, F>` shape was seen for the first time and there was no slot left to mint an id
into:

```text
boyko-B0502: QueryTypeId exhaustion: MAX_QUERY_TYPES = 1024 reached. This is a terminal panic —
             the process must restart. Enable the `big_query_table` cargo feature on boyko_ecs
             (raises the cap to 4096) or consolidate query shapes.
```

Raised from `crates/boyko_ecs/src/ecs/core/iters/query/query_type_registry.rs` (`register_new`).
The counter is **saturated** at the cap before the panic, so a re-entry cannot run it past.

## Why

A `QueryTypeId` indexes per-world slot arrays that are allocated to exactly `MAX_QUERY_TYPES`
entries. There is no id to hand back and no id that can be shared: two shapes on one id would mean
one shape reading the other's cached state, which is a wrong answer rather than a slow one.

It is a **panic and not a `Result`**, because the caller is `world.query::<D, F>()` — a function
whose contract is to return a query. Threading a fallible result through it would push the failure
to every call site in the engine to handle a condition none of them can do anything about.

This should be preceded by `boyko-W0501` at 75 % occupancy. If you are reading this page without
having seen that warning, either logging was not enabled or the table filled inside a single burst
— for instance a generic helper instantiated over a large type list at startup.

## How to fix

Identical to `boyko-W0501`'s, which is the warning that exists so this page is read early rather
than late:

- **Raise the cap.** Enable the `big_query_table` feature on `boyko_ecs`: 1024 → 4096 slots. The
  cost is the per-world slot arrays, which scale with it.
- **Spend fewer slots.** Every distinct `(D, F)` pair costs one, forever. A generic helper taking
  `Query<&T, With<Marker>>` over forty `T`s spends forty slots on one piece of logic; consolidating
  the shape, or moving the type parameter out of the query and into the body, recovers them.

There is no runtime recovery. The process must restart with one of the two changes above.
