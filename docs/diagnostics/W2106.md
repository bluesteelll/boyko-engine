# boyko-W2106 — an optional shadow chain's sets failed to build, so the chain is skipped

## What happened

One of the VB split's **optional** hardware-ray-traced shadow chains could not build its descriptor
sets, so the builder drained the partial ring and yielded `None`:

```text
boyko-W2106: vb_shadow_vis_set build failed (OOM-class) -- record_vb will skip the VB hwrt shadow
             chain this frame; the frame still renders
```

Three sites raise it, all in `crates/boyko_rhi_vulkan/src/present/targets.rs` and all behind
`feature = "hwrt"`, and the `{}` names which: `vb_shadow_vis_set`, `vb_shadow_atrous_sets`,
`vb_shadow_temporal_set`. `record_vb` finds the `None` and gracefully skips that chain — the frame
draws, without ray-traced shadows or without the temporal reproject.

`RatePolicy::Every`, for the same reason as [`boyko-E2103`](E2103.md): these run at target build and
at each resize, never per frame.

## Why

**A frame that renders is exactly the case nothing else reports.** There is no panic, no black
screen and no validation message — the shadows are simply the fallback ones, which look like a
lighting choice rather than a failure. Someone comparing two builds would attribute the difference
to the shadow work, not to a descriptor allocation that failed at the last resize.

`warn!` rather than `error!`, and the split from `E2103` is a **measurement rather than a matter of
taste**. Seven sites in that file degrade to `None`; `record_vb` consumes **four** of them with
`.expect(..)` (`present/passes/vb.rs:3706`, `:3776`, `:4291`, plus `thin_normal`) and **three** with
`if let Some(..)` (`:3988-3990`, `:4088`). The first group kills the frame; this group loses an
opt-in effect. In this registry the class letter *is* the level, so one code could not have carried
both — and a single code would have told an operator that the two outcomes are the same event.

## How to fix

All three are OOM-class descriptor allocations, so the levers are the same as `E2103`'s — lower the
extent, free VRAM — with one difference that matters:

- **Running without them is a supported configuration.** The hardware shadow chain is opt-in
  (`feature = "hwrt"` plus a config that arms it), so a device that cannot afford its sets can ship
  with it off rather than under-resourced. Turning it off deliberately is better than having it
  fail every resize, because the deliberate version is a state someone chose and this one is not.
- **If you are measuring shadow cost**, discard a run that printed this. The chain it was measuring
  did not execute, and a fast frame here means the work was skipped rather than done cheaply.
