# boyko-E2001 - a resource registry was dropped with live resources

## What happened

A `ResourceRegistry` reached its `Drop` while it still owned RHI resources:

```text
boyko-E2001: ResourceRegistry dropped with 6 live resource(s) (buffers=3, pipelines=1, shaders=0,
fences=2) - destroy_all was not called (LEAK)
```

Raised from `crates/boyko_rhi/src/handle.rs`. **Every one of those resources leaked.** The process
does not stop; there is nothing left that could free them.

## Why

The registry owns the backend's own types (`A::Buffer`, `A::ComputePipeline`, …), and none of them
can free itself: destroying a backend resource needs `&Device`, which a `Drop` impl does not have.
So the teardown discipline is structural — the owner **must** call `destroy_all(&device)` while the
device is still alive — and this record is the tripwire that fires when they did not.

`Drop` does not panic, deliberately: a panic during unwinding aborts the process, which would turn
a leak into a crash and lose whatever the unwinding was carrying. The `debug_assert!` beside the
report turns it into a hard test failure in debug builds; in release it is this record and nothing
else, which is why the record has to survive.

**The `stderr` fallback is part of the diagnostic, not a leftover.** With `BOYKO_LOG` unset every
target's runtime ceiling is `Off`, so the `error!` is never constructed — and `Drop` runs at
teardown, exactly when a sink is most likely gone already. The site emits, calls `flush()`, and
prints only when that answers `NoConsumer`. It is in `print_allowlist.txt` with that reason.

**This code exists because a gate found it, not because a plan listed it.** Five migration rungs
enumerated the crates they were converting, and `boyko_rhi` appeared in none of them; the site
surfaced the first time `print_census.rs` ran.

`RatePolicy::Every`. A process that leaks two registries has two leaks to report, and a latch would
report one.

## How to fix

- **Call `destroy_all(&device)` before the registry drops**, while the device that created the
  resources is still alive. That is the whole rule.
- **Assert it if the ownership is complicated.** `is_fully_drained()` is public for exactly this:
  an owner that cannot easily see its own teardown order can check before dropping.
- **Read the per-kind counts.** They say which `register_*` calls have no matching `take_*` — a
  registry leaking only fences usually means a frame path that early-returns before its fence is
  reclaimed, which is a different bug from one leaking buffers.
- **A leak on an error path is the common shape.** The `destroy_all` call is often on the success
  path only; the failure branch returns and the registry drops. `boyko_app`'s boot-failure arms
  are written the other way round on purpose and are worth reading as a model.
