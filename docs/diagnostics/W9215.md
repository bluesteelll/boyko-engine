# boyko-W9215 — a telemetry write failed and streaming was disabled

## What happened

A telemetry window's single `write_all` returned an error, and the writer switched streaming off for
the rest of the session:

```text
boyko-W9215: a telemetry write failed; streaming is disabled for the rest of this session
```

Raised from `crates/boyko_app/src/profiling/stream.rs` through
`boyko_diag::loss::DiagFlag::TelemetryWriteFailed`, emitted by
`crates/boyko_ecs/src/ecs/core/profiling/diag.rs` (`report_telemetry_write_failed`) at the next fold.

The file keeps **every whole block written before the failure**. A decoder reads them all, reports
`blocks_ok` and `records_ok`, and states the leftover bytes as `truncated_tail_bytes` rather than
decoding them.

## Why streaming is disabled rather than retried

A write that failed inside one frame will fail inside the next one. Retrying would put an unbounded
number of failing syscalls on the dispatcher at the exact moment the machine is in trouble — a disk
that is full, a volume that was removed, a quota that was hit — and would turn a lost telemetry
window into a frame-rate collapse.

**Never a panic, never a retry in-frame, and never a second thread to absorb it.** The engine's only
threads are the pool's; a telemetry failure does not get to change that.

## Why this is a different code from `W9214`

The two states differ in what a reader is left holding. `W9214` leaves **no file**. This leaves a
file with a **stated end**. Reporting both as one code would send an operator to check permissions
on a disk that was simply full halfway through a session.

## What the loss bound is

**At most one window.** There is no cross-window buffering: each window is encoded into a `.bss`
double buffer and handed to one `write_all`, so the only data a failure can lose is the window that
failed. A partial write tears exactly one block, and the block framing — magic, length, sequence and
CRC — is what lets the decoder detect that tear instead of decoding half a record as data.

What this bound does **not** cover, stated so it is not assumed: power loss and a driver hang. No
in-process mechanism can cover either.

## What causes it

- The disk filled (`ENOSPC`). This is the shape the framing was designed against: `write_all`
  returns *after* a partial write, so the file ends mid-record.
- A removable volume was unplugged mid-session.
- A quota or a filesystem limit was reached.
- The file was deleted or replaced by another process while open.

## Why it is a warning and not an error

The engine is fine and the frames are fine. What a reader must know is that the stream **stops
here** — a file that simply ends reads as a session that ended, and this code is the difference.

## Why it fires once

`RatePolicy::Once`. Streaming is off after the first failure, so the condition cannot recur; the
latch is belt and braces.

## How to fix

- Free space on the volume, or point the telemetry path at one with room.
- Size the session: a shipping build writes roughly 2.9 MB/h, a `dev` build about ten times that.
- Set `max_bytes` so the writer rotates instead of growing without bound.
