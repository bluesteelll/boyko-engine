## 1. Thesis + integrated model

### 1.1 The one-sentence thesis

> **Put a real 3D frame on screen that composites rasterized meshes and a sphere-traced SDF in one shared-depth deferred buffer, and resolve real rigid-body contacts on the CPU against colliders that can be sampled from that same SDF — reusing the proven zero-readback GPU spine and the proven CPU scheduler, with the in-house Soft-Step rigid solver as the only shipped solver, and deferring every heavy net-new subsystem (brick atlas, clipmap LOD, JFA regen, GPU-driven indirect, HW ray tracing, continuum solvers) behind seams already cut.**

### 1.2 Why these three pillars are one slice, not three

The binding session conclusion fixes the integrated model, and it is **load-bearing for the whole plan**:

- **SDF is the shared representation.** The render pillar **draws** with it (sphere-trace the field into the deferred G-buffer); the physics pillar **samples** it for collision queries (distance = penetration depth, gradient = contact normal — §15/§16 of the SDF doc). One representation, two consumers — and, in the basic slice, **three evaluator implementations** of the same distance math (GPU HLSL, CPU render-side eval, CPU physics-side query); the conformance obligation that keeps all three in agreement is W4 / §3.4 / OQ-3.
- **The CPU/GPU split is fixed and non-negotiable** (honoring the session conclusion): **rigid-body constraint RESOLVE and AI live on the CPU** (iterative, serial, branchy, low-N, gameplay-coupled); **the GPU owns rendering + homogeneous large-N mass** (SDF field eval/raymarch now; particles/soft/fluid later). **A CPU system touching GPU-resident bytes is forbidden by construction** (a CPU `Access` never matches a GPU archetype — Phase-4 D4, Phase-5 MF-4/C1).
- **Hybrid mesh+SDF is never fused.** Each draw/query routes to whichever representation answers cheapest (SDF doc §15.0). Meshes coexist with SDF; SDF is the *extensible* base. The render slice proves the **shared-depth seam** (§15.1) so the two coexist correctly; it does not fuse them.
- **The physics solver is fully in-house — RESOLVED, not an open question.** The in-house Soft-Step / sequential-impulse 3D rigid solver (CPU, on the Phase-9 work-stealing threadpool for the `par_iter_mut` integrate stage; single-threaded solve) is the **only shipped solver**. The `RigidSolver` seam is preserved for experimentation, but **no Rapier/Jolt/parry FFI is ever a shipped or distributed path** — an FFI backend is at most a private offline correctness oracle, never linked into a release. There is no in-house-vs-FFI open fork (see §3.7).

**What is genuinely new in this slice** (everything else is HAVE, reused):
1. **RHI graphics surface**: fill the `#[cold]`-erroring stubs (`create_texture`, `create_sampler`, `create_graphics_pipeline`, `create_bind_group_layout`, `create_bind_group`) + add a `begin_rendering`/`end_rendering` + `draw`/`bind_graphics_pipeline`/`bind_vertex_buffer`/`bind_index_buffer` encoder surface + the `ImageBarrier` seam (Phase-2-3 of RHI plan, now needed). 2. **`boyko_render` graphics path**: a minimal **deferred G-buffer** + **one sphere-tracing compute/fragment SDF pass reading shared depth** + **one lighting pass** + **mesh draw**. Sphere-tracer is the **universal software fallback** (no atlas/clipmap/JFA — evaluate an analytic SDF or a single dense low-res 3D texture).
3. **SDF representation (minimal)**: a **CPU+GPU-shared analytic edit-list** (small, fixed-cap, uploaded once per change to a uniform/SSBO) — **NOT** the brick atlas / clipmap / BVH-dirty-region machine (that is the deferred extensible body, SDF doc §6/§7/§8). 4. **Physics 3D + real in-house resolve**: move the `boyko_physics` math/colliders from `Vec2` to `Vec3`/quaternion (type-swap the alias the foundation reserved — a type-swap *plus genuine 3D math additions*, P1), then add a **real sequential-impulse Soft-Step rigid solver** behind the existing `RigidSolver` seam (the largest net-new algorithm in the phase, P2 / §3.5; `SoftStep3D` is the shipped real backend, `NoopSolver` stays the crate default), and add a **CPU SDF collision query** (shape↔field) feeding the same `Manifold` currency.

## 2. Smallest-vertical-slice ordered roadmap

Each slice **compiles, demonstrates standalone, keeps the 0%-gate, and keeps every existing test + Miri-TB suite green** — with the one explicit serialization caveat noted in the ordering summary (SDFrep/P3 are gated behind OQ-3, W5). The ordering is a single linearized critical path with two parallelizable side-tracks (physics 3D, SDF representation) that do not gate the render spine. Acceptance tests are concrete and oracle-based (validation-layers-fail-the-test + golden-buffer/golden-image where GPU; Miri/unit where CPU).

### Dependency & ordering summary

```
S0 (RHI graphics surface)  ──▶  S1 (mesh→G-buffer→light→present)  ──▶  S2 (SDF sphere-trace shared-depth)  ──▶  S3 (hybrid composite)
                                                                                   ▲
P1 (physics 2D→3D type-swap) ──▶ P2 (real Soft-Step 3D resolve) ──────────────────┼──▶ P3 (CPU shape↔SDF query → Manifold)
                                                                                   │
        OQ-3 (close to leaf crate) ──▶ SDFrep (analytic edit-list, CPU+GPU) ───────┘   (feeds both S2 and P3)
```
- **S0 → S1 → S2 → S3** is the render critical path (serial).
- **P1 → P2 → P3** is the physics track; P1/P2 are independent of the render path (CPU-only, no graphics) and can land in parallel with S0/S1. **P3 depends on SDFrep** (it samples the shared field).
- **SDFrep** (the minimal analytic edit-list, shared CPU+GPU) is a small leaf that **both S2 and P3 consume**. **It is NOT freely parallelizable with S0/S1 until OQ-3 is closed** (W5): SDFrep physically lives in or beside `boyko_render`, and the shared evaluator code + the layout fingerprint must have a single home before SDFrep lands, or `boyko_physics` would have to depend on a half-built `boyko_render::graphics` (the forbidden render↔physics coupling). **OQ-3 is closed to the leaf crate now** (§3.6), so SDFrep parallelizes with S0/S1/P1 against the leaf crate, not against `boyko_render`.

### Slice S2 — SDF sphere-trace pass reading shared depth

- **Goal.** Add a sphere-tracing pass that evaluates the **minimal analytic SDF edit-list** (SDFrep) and writes the SDF surface into the **same** G-buffer, **reading the existing mesh depth as a ray-distance bound** → correct mesh↔SDF occlusion for free (SDF doc §15.1). Software sphere-tracer is the **universal fallback** (no atlas/clipmap/JFA; HW ray tracing is a deferred optional backend, not here).
- **First-principles cost ceiling (labeled estimate, NOT a benchmark, O4).** Per-pixel sphere-trace is `O(edits) × O(march_steps)` per ray. The basic slice commits to a hard ceiling: **≤ 64 edits in the list, ≤ 128 march steps per ray, sphere-traced at half-resolution** (1/4 the pixels of the present surface) for the SDF pass, with the analytic eval staying within an L1-resident edit-list working set (64 × `size_of::<SdfEdit>()` ≈ 64 × 96 B ≈ 6 KB, comfortably inside L1d on the GPU's per-lane registers/L1 path is N/A — this is the GPU eval; the bound exists to keep the analytic march tractable, not to fit a CPU cache). This ceiling is the exact wall the deferred §6-§8 brick cache removes when the list grows; it is recorded so "fine for a small list" is a stated budget, not an assertion. The numbers are design ceilings to validate against at kickoff, not measured.
- **Files.**
  - `crates/boyko_render/shaders/sdf_spheretrace.hlsl` → `.spv`: per-pixel sphere-trace the edit-list (union/subtraction/intersection + smooth-min, SDF doc §2), bounded by the sampled mesh depth, writing G-buffer depth/normal(field gradient)/albedo/material on hit. **This HLSL is the third evaluator (W4): it is a hand-port of the same IQ primitive distance + smooth-min math as the two Rust evaluators, and its primitive set is FROZEN to exactly the Rust primitive set for the basic slice (sphere/box + union/sub/intersect + smooth-min — no shader-only primitives).**
  - `crates/boyko_render/src/graphics/sdf_pass.rs`: bind the SDFrep edit-list buffer (SSBO/uniform) + the G-buffer depth as input; dispatch; barrier (depth read-after-write from the mesh pass — lowered via the existing `PlannedBarrier`/superset-correct lowering, Phase-5 D6).
  - `crates/boyko_render/src/components/sdf.rs`: `SdfVolume` component (a handle to an edit-list region) as an ordinary CPU column (the CPU owns *which* edits exist — structure; the GPU owns *evaluating* them — data-parallel).
- **HAVE vs net-new.**
  - **HAVE:** SDFrep (the shared edit-list, landed as a leaf before S2), the G-buffer + depth from S1, the barrier-lowering machinery, the compute dispatch path, `create_texture(D3)` (if a dense low-res field is used instead of pure analytic).
  - **Net-new:** the sphere-trace shader; the shared-depth read seam; the SDF pass wiring + its barrier into the frame sequence.
- **Acceptance test.** `tests/sdf_spheretrace_golden.rs` (headless offscreen): render a known analytic scene (one sphere edit subtracted from one box edit) → golden-diff the surface region; a **shared-depth occlusion test** — place a mesh quad in front of the SDF and assert the SDF is correctly occluded (depth-bounded march). Validation-clean. **The three-way conformance test (`cpu_gpu_sdf_agreement`, see P3 / W4) is a REQUIRED acceptance gate that the SDF pillar shares with S2, not optional.**
- **CPU/GPU split.** CPU owns the edit-list contents (gameplay edits, branchy); GPU evaluates per-pixel. Edit-list re-upload happens only on change (pay-for-what-you-use, SDF doc §15.0), at setup/edit-time, not per frame.

### Slice P1 — Physics 2D → 3D type-swap (plus genuine 3D math additions)

- **Goal.** Move the `boyko_physics` foundation math and colliders from 2D (`Vec2`) to 3D (`Vec3` + a quaternion rotation), honoring the foundation plan's reserved type-swap seam. **No new resolve algorithm yet** — `NoopSolver` still the default; this slice changes the *types* AND adds the genuine 3D math (angular integration via quaternion, the inertia tensor) so 3D bodies integrate and collide-pair correctly. This is a type-swap **plus** real 3D additions, not a pure alias flip (§3.5).
- **Files.**

### Slice P2 — Real in-house Soft-Step 3D rigid resolve (the largest net-new algorithm in the phase)

- **Goal.** Replace the *demonstrated* solver from `NoopSolver` to a **real sequential-impulse Soft-Step rigid solver** (Catto Box2D-v3 substep + soft-constraint lineage, 3D) behind the existing `RigidSolver` seam. **This is the single largest net-new ALGORITHMIC chunk in the entire phase (W1) — it is NOT a type-swap of P1.** It is **CPU, iterative, serial** (the session conclusion). `NoopSolver` remains the crate default; `SoftStep3D` is the shipped real backend. **This is the only shipped solver — fully in-house (§3.7); no FFI backend is ever distributed.** Budget this slice as the heaviest correctness surface in the phase.
- **Net-new, named as four genuinely-new 3D sub-items (W1-a), each with its 3D-specific risk** (do NOT let these hide behind a single "sequential-impulse" bullet — treating P2 as "port the 2D solver to Vec3" makes `stacking_is_stable` fail as missing-tensor-rotation correctness bugs that look like tuning bugs):
  1. **3D contact constraint Jacobians with the inertia tensor.** The angular term is `r × n` transformed by the full `Mat3` `inv_inertia`, **rotated into world space each substep** from the body orientation (`R · I_body⁻¹ · Rᵀ`).   3. **Quaternion integration + normalization drift consumption.** The solver must consume the P1 quaternion orientation correctly each substep to rotate the inertia tensor; orientation renormalization (P1) interacts with the substep loop.
  4. **Warm-start keyed by 3D `feature_id`.** Warm-starting across 3D contact features (face/edge/vertex) is a real correctness surface — 3D feature IDs are materially harder to make stable across frames than 2D, and an unstable key silently kills warm-start convergence.

## 3. Cross-pillar decisions (RESOLVED)

### 3.1 The SDF representation is a CPU-authoritative analytic edit-list, GPU-mirrored (basic slice)

**Decision.** For the basic slice the SDF is a **small analytic edit-list whose authoritative copy is CPU-resident**, mirrored to a GPU SSBO on change. **NOT** the brick atlas / clipmap / BVH machine (deferred). **Why:** (a) it makes both consumers (render sphere-trace, physics query) trivial and lets physics evaluate **without any GPU readback** (§3.4); (b) it is the SDF doc's own §2-§4 starting layer; (c) it is pay-for-what-you-use (re-upload only on edit). **Trade-off:** per-pixel sphere-tracing an analytic list is O(edits)×O(march-steps) per ray (the §S2 cost ceiling: ≤64 edits, ≤128 steps, half-res) — fine for a small list (the basic slice), and the exact wall the §6-§8 brick cache exists to remove **when the list grows** (deferred, §6). **Alternative rejected:** GPU-resident brick atlas now — over-builds the frontier subsystem before the load-bearing render+physics+integration thread is proven on screen (the upstream Phase-0 thesis lesson: prove the load-bearing risk in miniature first).

> **Sidebar — external validation (gpecs) + the raw-Vulkan barrier caveat (C2).**
> The zero-readback GPU-resident-column model this plan rests on is **independently corroborated** by `tuguzT/gpecs` (a wgpu + rust-gpu GPU-ECS, cloned and inspected): it uses the **same model** — component columns as GPU STORAGE buffers that stay **resident across steps**, **one compute-pass dispatch per system** over those buffers, and **zero per-step readback** (its `GpuExecutor::execute` records compute passes + submits; readback exists only as an explicit out-of-band `into_context`/transfer path, never per step; its n-body example renders a `VERTEX | STORAGE` buffer **directly**, no copy-back). This independently validates our design.
> **The honest caveat:** gpecs needs **no explicit barriers** in `execute()` only because **wgpu auto-tracks resource state and inserts them** — a WebGPU luxury we do **NOT** get on raw Vulkan. Therefore our explicit `PlannedBarrier` lowering (§5.2) is **REQUIRED, not optional, and not over-engineering** — it is the unavoidable tax of the no-wgpu / raw-FFI / native-Vulkan decision. gpecs validates the *design*; the explicit barrier machinery is the *cost* of getting that design without wgpu's auto-tracking.

### 3.2 Hybrid mesh+SDF: shared-depth deferred buffer, never fused, route per consumer

**Decision.** Meshes rasterize into the deferred G-buffer; the SDF sphere-traces into the **same** buffer reading the **same** depth (S2/S3); one lighting pass over both. **Routing is per-draw/per-query**, not a fusion (SDF doc §15). **Why:** correct mesh↔SDF occlusion falls out of the shared depth for free; lighting/shadow/post is written once; each representation is consumed where it is cheapest. **Trade-off:** the implicit↔explicit boundary (mesh surface meets SDF cap) shows a seam (blend or hard edge) — accepted for the basic slice (SDF doc §15.2 "where the honest overhead lives"). **Deferred:** tile-culling the raymarch (SDF doc §15.1), SDF-cut mesh holes (§15.2), two-way mesh↔SDF conversion (§15.3).

### 3.3 The CPU/GPU split is fixed: rigid RESOLVE + AI on CPU; render + large-N mass on GPU

**Decision.** Honored verbatim from the session conclusion. Rigid-body constraint resolve (P2) and AI are **CPU, iterative, serial, branchy, low-N**. The GPU owns rendering (S1-S3) and is reserved for homogeneous large-N mass (particles/soft/fluid — deferred). **Why:** a round-trip to ask the GPU a branch (~1-2 µs, RESEARCH §2) ≫ a CPU branch (~1 ns); SIMT divergence punishes branchy low-N work; the rigid solver's per-contact loop is inherently serial (a pair `(a,b)` writes both bodies → parallel pair-solve races, PHYSICS-FOUNDATION D4). **GPU-resident-zero-readback is opt-in per archetype**, with a ~3M-entity break-even (Phase-4 §1.1) — rigid bodies are far below it. **Trade-off:** the CPU solver caps rigid-body count; that is the correct trade for the basic slice (the session conclusion accepts it). **A CPU system touching GPU-resident bytes is forbidden** (Phase-4 D4, Phase-5 MF-4/C1 — the residency bit + query-skip + null-column guard already enforce it).

### 3.4 Physics-reads-SDF-without-readback — the honest concrete answer

**This is the load-bearing cross-pillar question. The honest answer is: the basic slice avoids the readback problem entirely by NOT making the SDF GPU-resident-authoritative — and that is the correct foundation design, not a dodge. Concretely: one field, two CPU evaluators (render-eval + physics-query) plus the GPU HLSL evaluator, all reading independent copies of the same small CPU-authored data; zero readback by construction.**

The dilemma: the session conclusion says **a CPU system touching GPU bytes is forbidden**, yet physics (CPU) must collision-query the SDF. Three candidate resolutions, evaluated:

| Option | Mechanism | Verdict |
|---|---|---|
| **A — CPU-authoritative edit-list, GPU-mirrored (CHOSEN for basic slice)** | The SDF's source of truth is a small CPU-resident analytic edit-list; the GPU gets a copy for rendering; **physics evaluates the CPU copy directly (no GPU touch at all)**. | **CHOSEN.** Zero readback; zero CPU-touches-GPU-bytes; both consumers read independent copies of the same small data; the evaluator math is shared CODE in the `boyko_sdf_math` leaf (§3.6, "share the CODE, not the instance"). The only honest cost: the field is evaluated by three implementations (per-pixel on GPU HLSL, per-query on CPU physics, per-sample on CPU render) — the W4 conformance test keeps them in agreement; acceptable for a small analytic list. |
| **B — GPU-resident brick field, CPU reads back the queried region** | Physics asks the GPU for distances at query points; GPU writes them to a host-visible staging buffer; CPU reads them. | **REJECTED for the frame path.** This is **exactly the Regime-B readback trap** (RESEARCH §2, the Svelto trap: a `2·N·B` PCIe tax + a per-frame CPU↔GPU round-trip + a fence stall). It violates "a CPU system touching GPU bytes is forbidden." Permissible **only** as a test-only oracle (the `cpu_gpu_sdf_agreement` test in P3), never on the frame path. |
| **C — Physics runs ON the GPU too (GPU rigid solver)** | Move rigid resolve to a compute shader so it co-resides with the SDF. | **REJECTED by the session conclusion.** Rigid resolve is iterative/serial/branchy/low-N — the GPU's worst case. This is the explicit thing the session conclusion forbids. (Reserved for the deferred large-N continuum path: particles/soft/fluid that sample the GPU field *on the GPU* — that path never reads back either.) |

**The resolved rule (for the whole engine, stated honestly):**
- **Basic slice:** SDF is CPU-authoritative + GPU-mirrored (Option A). Physics evaluates the CPU copy. **No readback, no forbidden touch.**
- **When the SDF graduates to a GPU-resident brick atlas (deferred, §6):** the field becomes large and GPU-authoritative. At that point **CPU physics must NOT read it back per frame**. The forward design (recorded here so the seam is reserved, not built): the **collision-mesh-from-SDF** path (SDF doc §9 / §16.2) — the GPU (or a CPU thread pool, Turitzin's choice) generates a **low-res triangle collision mesh from the dirty SDF bricks**, and the CPU rigid solver collides against **that mesh**, not the live field. The mesh is produced on the producing side and handed to physics as ordinary CPU geometry — **the boundary is crossed by a structural hand-off (a mesh chunk), not a per-query byte read** — exactly the §16.5 routing rule ("SDF decides where; the solver decides how"). **This is DEFERRED; the basic slice does not need it** because the analytic edit-list is small enough to evaluate directly on the CPU.

**Why this is the right foundation answer and not a cop-out:** the basic-slice job is the smallest end-to-end thread. Making the SDF small + CPU-authoritative is the *correct* design at this scale (it is literally the SDF doc's §2 starting point), and it makes the integration sound *by construction* (no readback can exist if the CPU never needs to touch GPU bytes). The hard readback-avoidance problem is **real but only appears at the deferred brick-atlas scale**, where the collision-mesh hand-off (§9) is the established answer. We state both, build the first, reserve the seam for the second.

### 3.5 3D from the start; 2D foundation is type-swapped, but P2 is a real algorithm, not a swap

**Decision.** The physics foundation's reserved `Vec2 → Vec3` + `MAX_CONTACT_POINTS 2 → 4` type-swap is executed in P1 (the foundation plan's OQ4 + MINOR-3 reserved exactly this). Rotation moves from scalar `f32` (2D) to `Quat` (3D), and inertia from scalar `f32` to a `Mat3` tensor — these are genuine 3D math additions, not just aliases, and P1 calls them out as net-new. **P2 (the Soft-Step resolve) is the largest net-new ALGORITHM in the phase, NOT a type-swap (W1)**: the rotated inertia tensor, the 2-DOF friction cone, quaternion-driven substeps, and 3D-feature warm-start keying are all genuinely new and must be budgeted as the heaviest correctness surface (P2 enumerates the four sub-items). The "type-swapped, not rewritten" framing applies to P1 only; P2 is rewritten. **Why:** the render is 3D; a 2D physics foundation cannot collide against a 3D SDF or 3D meshes. **Trade-off:** the `Manifold` may grow toward 2 cache lines with 4 points + `Vec3` normal + `Vec3` anchors — re-pinned with an honest `const assert` (the live `:84-86` comment does NOT pre-clear the `Vec3` case; recompute at kickoff; forced-fit rejected; if it spills, the bound is updated truthfully, OQ-4). **Alternative rejected:** keep 2D physics + a separate 3D path — forks the seam and contradicts "the basic slice must be 3D."

### 3.6 Shared SDF evaluator lives in a `boyko_sdf_math` leaf crate (OQ-3 — CLOSED to the leaf)

**Decision.** The union/sub/intersect/smooth-min primitive distance math lives in **a tiny new `boyko_sdf_math` `no_std` leaf crate** — one source of truth, depended on by both `boyko_render::sdf` and `boyko_physics::sdf_query` ("share the CODE, not the instance" literally). **Why this is now closed rather than open:** (a) it is the only option that keeps the std430 layout fingerprint (§3.8 / C1) as a **single source of truth** rather than duplicated; (b) it makes SDFrep parallelizable with S0/S1 without `boyko_physics` depending on the half-built `boyko_render::graphics` (W5); (c) it avoids the duplicated-math drift that the conformance test would otherwise have to police across two Rust copies. The HLSL shader remains a necessarily-separate third evaluator (W4 — it cannot share Rust code); the W4 three-way conformance test is the oracle that keeps it from drifting. **Alternative rejected:** duplicate the math + a golden conformance test, no new crate — rejected because it scatters the layout fingerprint and re-introduces the render↔physics serialization hazard of W5. **Trade-off:** one more crate in the workspace — accepted; it is a leaf with no graphics deps.

### 3.7 The physics solver is fully in-house — CLOSED, no FFI shipped path

**Decision.** The in-house Soft-Step / sequential-impulse 3D rigid solver (P2) is the **only shipped solver**. The `RigidSolver` trait seam is preserved purely for experimentation and for the `NoopSolver` default. **A Rapier/Jolt/parry FFI backend is NEVER a shipped or distributed path** — at most a private offline correctness oracle (a test-only comparison harness), never linked into a release build, never behind a public feature flag that ships. **Why:** owner decision, RESOLVED; the no-third-party rule and the "ultimate, first-principles" mandate make the in-house solver the product, not a stopgap. **Why this closes a former open fork:** earlier drafts hedged "physics *may* take a dep behind the seam if perf demands" — that hedge is removed. The seam stays (it is good engineering and proves swappability via `seam_swap_noop_vs_softstep`), but the swap target is never a distributed FFI library. **Trade-off:** all solver perf/correctness debt is ours to carry — accepted, consistent with the in-house mandate.

### 3.8 CPU↔GPU component-layout contract — a Slice-0 obligation (C1, the gpecs addition)

**Decision.** Every GPU-resident component / buffer struct (the SDFrep `SdfEdit`, the S1 mesh vertex layout, and any uniform block) carries a **compile-time CPU↔GPU layout contract** so that a mismatch between the Rust `#[repr(C)]` struct and the std430 SSBO layout the HLSL shader expects is a **BUILD ERROR, not silent GPU corruption**. This is the one failure mode gpecs surfaces (via its shared `_types` crate + `ComponentDescriptor`); our in-house analog reuses the proven serialization `layout_fingerprint` pattern.

**Why critical (not optional).** A "std430-compatible" claim verified only by a runtime golden test is the silent-corruption class: std430 alignment rules differ from Rust `#[repr(C)]` (`Mat4` column alignment, the `u8 + u8 + f32` head where std430 rounds member offsets, the 16-byte `vec4` alignment for `params`). A mismatch makes the GPU read garbage at a shifted offset — and **validation layers will NOT catch a layout-offset error** (the buffer is the right size; the bytes are just interpreted wrong). The golden test catches it only if the author hand-encoded the right golden — the same error surface restated.

**What is built (owned by SDFrep for `SdfEdit`, by S1 for the mesh vertex layout + uniform blocks):**
- A **compile-time std430 assertion** per GPU-resident struct: `const _: () = assert!(offset_of!(SdfEdit, transform) == EXPECTED_STD430_OFFSET && size_of::<SdfEdit>() == EXPECTED_STD430_SIZE && align_of::<SdfEdit>() == 16)` (and analogous per-field offset asserts).
- A **layout fingerprint** (analogous to the serialization `layout_fingerprint`) computed from field offsets/sizes/alignments, asserted at compile time against a value derived from the shader side — so a mismatch is a build error.
- **Who produces the shader-side expected layout (resolved, answering the critic's OQ-1 follow-up):** a **build-script step that runs DXC reflection** on the committed `.spv`/HLSL and emits the expected std430 offsets/size as generated constants, which the `const assert` checks against. This makes the contract a **build-script obligation that feeds a `const assert`** (not a hand-maintained constant, which would itself be an error surface). If DXC reflection is impractical at kickoff, the fallback is a single hand-maintained constant **in the `boyko_sdf_math` leaf** (one place, OQ-3-closed) with a `// SAFETY/CONTRACT:` note that it must be regenerated when the shader struct changes — but the build-script reflection path is the target.
- The fingerprint lives in the `boyko_sdf_math` leaf (OQ-3 closed to the leaf, §3.6) as the single source of truth.

**Trade-off.** A build-script + DXC-reflection step adds setup-time complexity — accepted; it is the only thing that converts a silent-GPU-corruption class into a compiler error.

## 5. 0%-gate + soundness obligations

### 5.1 0%-gate (INVIOLABLE)

- **A world using no Phase-6 feature pays at most one `test`/`jz`.** The render and physics pillars are **separate crates not linked** into a CPU-only ECS world (the proven `boyko_physics`-foundation 0%-gate: not linked → zero cost). The graphics passes only run when a `boyko_render` schedule is added.
- **Hot loops stay `cargo-asm` byte-identical:** `ComponentPool::row_ptr`, `Query::for_each_chunk`, query iter, the scheduler `find_ready`. Phase 6 adds **no new core hot-path branch** — `Mesh`/`Transform3D`/`Camera3D`/physics-3D components are ordinary CPU columns (no new residency/flag logic beyond the Phase-4 bit already gated). **Acceptance:** A/B `cargo asm` spot-check on those four symbols, ±2% on `bench_spawn_10k`/`bench_iter_*`/`bench_schedule_50_systems` vs the pre-Phase-6 baseline.
- **The GpuSystem record/submit is the only dispatcher-solo addition** — it rides the existing Phase-4 `SystemKind::GpuCompute` + `running == 0` + `DispatcherToken` path (no new scheduler branch; the gate is the existing residency/kind bit).
- **No `Vec::new`/`HashMap`/`Box<dyn>` on any frame path:** edit-list is fixed-cap preallocated; G-buffer/pipelines/bind-groups created at setup; per-frame is record-only (the proven Phase-5 steady state). The solver's `SolverScratch` buffers are preallocated + reused (PHYSICS-FOUNDATION D4).
- **`boyko_ecs` stays graphics-pure:** purity grep (`grep -r "boyko_rhi|vulkan|Vk|gbuffer|spheretrace" crates/boyko_ecs/src` finds nothing) must hold post-Phase-6. Phase 6 does **not** touch `boyko_ecs` — `Mesh`/`Camera3D` live in `boyko_render`, `Transform3D` in the `boyko_scene` leaf (OQ-1/OQ-2 closed, §3.9); all are graphics-pure POD components defined outside core, keeping core untouched.

### 5.2 Soundness obligations

- **The GPU half is NOT Miri-checkable** (VRAM mapping, raw FFI, GPU↔CPU buffers — RESEARCH §2 caveat). The soundness oracle is, in order: **(a) Vulkan validation layers wired to FAIL the test** (every GPU test, debug build, headless — `debug.rs` HAVE); **(b) deterministic golden-buffer/golden-image diffs** (every render acceptance test); **(c) the existing CPU Miri-TB suites stay green** (the device-pool variant is `cfg(miri)`-gated host-only; no new core `unsafe` under Miri). **Layout-offset bugs are NOT caught by (a) or (b) — they are caught by the §3.8 compile-time std430 contract (a build error), which is the third oracle.**
- **Every new `unsafe` carries a `// SAFETY:` comment** stating invariants (the `boyko_rhi_vulkan` FFI discipline — the texture/image/graphics-pipeline creation is bounded `unsafe`, `#[repr(C)]` struct-filling + PFN calls, each documented). **The graphics-pipeline-creation block additionally documents the attachment-format-matching invariant (W2-b / S0 SAFETY obligation).**
- **The dangling-Host-base + CPU-can't-touch-GPU-bytes invariants are already enforced** by the Phase-4/5 residency bit + dual query-skip + null-column guard (Phase-5 Mini-Critic C1/C2). Phase 6 adds **no GPU-resident archetype** (meshes/transforms/SDF-edit-lists are CPU-resident; the GPU buffers are device-local resources owned by `boyko_render`, not ECS columns) → the GPU-ECS soundness surface is **unchanged**, and Phase 6 does not re-open it. **Obligation:** confirm at kickoff that the render path uses `GpuColumnManager` device *buffers* (resource registry), not GPU-resident ECS *columns* — the basic slice does not need GPU-resident archetypes (that is the deferred ~3M-entity regime).
- **Physics solve is single-threaded** (P2) → no new data-race surface; integrate is `par_iter_mut` over disjoint rows (the engine's verified model); write-back at the apply-window (`running == 0`, the proven race-free tick). The CPU SDF query (P3) reads a CPU-resident edit-list (no GPU touch) → no new `unsafe`.
- **`RhiContext` stays `NonSendResource`, reached only via `DispatcherToken` on the dispatcher** (Phase-5 MF-5 Option C) — the graphics passes record/submit through this; the worker-reachable `nonsend_resource_mut` is deleted (the compile_fail test stands). **Obligation:** the new graphics encoder verbs are recorded only inside `GpuSystem::run_dispatcher` (token-gated), never reachable from a worker.
- **Barrier correctness is superset-correct AND REQUIRED on raw Vulkan** (Phase-5 D6; §3.1 sidebar): the new mesh-pass→SDF-pass→light-pass image barriers over-synchronize rather than miss; a `sync_validation` golden test proves a wrong/omitted barrier trips the validation layer. **This is load-bearing, not decorative — gpecs gets away without explicit barriers only because wgpu auto-inserts them; raw Vulkan does not, so this lowering is the unavoidable cost of the no-wgpu decision (C2).**
- **Determinism contract** (physics): keyed on `BodyIndex` = archetype row order = spawn order; deterministic-across-runs requires deterministic spawn (IM-2 — single-threaded tests satisfy it; a content-defined key is the deferred path).

## 7. Design decisions resolved + kickoff verification (no open owner-decisions)

Every performance / architecture fork is **decided here on first-principles grounds** — none is deferred to the owner. Perf/architecture choices are an engineering responsibility; only values / scope / dependency-philosophy calls (e.g. the fully-in-house solver, §3.7) were the owner's. The items below that remain "open" are **kickoff *verification* obligations** (measurements), not choices.

**Resolved (former forks, now CLOSED):**
- **In-house-vs-FFI solver** — CLOSED to in-house (§3.7).
- **Shared-evaluator crate** — CLOSED to the `boyko_sdf_math` leaf (§3.6 / OQ-3).
- **`Transform3D` ownership + physics/render unification** — CLOSED to a `boyko_scene` leaf + demo-glue sync system (§3.9).
- **Layout contract** — CLOSED to a build-script DXC-reflection `const assert` (§3.8).
- **OQ-A — SDF representation for the basic slice → CLOSED to a pure analytic edit-list.** *Why (first principles):* it is the smallest real mutable-SDF base and — decisively — the only representation that resolves the cross-pillar no-readback crux *for free*. The authoritative field is the small analytic edit-list, evaluated by the GPU sphere-tracer for render AND analytically on the CPU for physics collision queries: one source of truth, two evaluators, ZERO readback. A baked dense 3D texture would force either a per-frame GPU→CPU readback (forbidden) or a duplicated CPU bake for physics, and it pulls in `create_texture(D3)` + a fixed memory cost for no benefit at the basic slice's handful-of-primitives edit count. The per-pixel cost of analytic eval only becomes a wall at dozens-plus overlapping edits — which is exactly the job of the deferred performance extension (grid distance cache → 8³ brick map/atlas → geometry-clipmap LOD, SDF doc §4–§8), which augments/replaces the analytic eval *without reshaping the base*. Analytic is therefore the max-perf-*aware* base; the cache hierarchy is the documented perf scaling. **S2 binds an SSBO edit-list, not a sampled 3D image.**
- **OQ-B — basic-slice render path → CLOSED to a minimal deferred G-buffer.** *Why (first principles):* the hybrid mesh+SDF shared-depth composite with **one lighting pass over both** (SDF doc §15.1) is the whole point of the render slice, and deferred makes it natural — meshes rasterize into the G-buffer, the SDF sphere-traces into the *same* buffer against the *same* depth, one pass shades both, with no duplicated lighting between a mesh fragment shader and the SDF raymarch (which forward would force). Deferred is also the natural substrate for the **confirmed-future RT-lighting** (it reads the G-buffer normal/depth/albedo), so forward would mean reworking the entire shading topology when RT-lighting lands. The G-buffer bandwidth cost is modest at the basic slice and is the target of the documented perf extensions (Hi-Z tile cull, half-res + TAA, a visibility/deferred-texturing buffer). **S1 commits the deferred attachment set.**
- **OQ-5 — SDF sphere-trace pass → CLOSED to a compute pass.** *Why (first principles):* it reuses the proven Phase-5 compute-dispatch + barrier-lowering spine (the `GpuSystem` path) instead of standing up a second graphics-pipeline surface for the SDF pass, writes the G-buffer as `STORAGE` images, and stays on the same uniform compute model as the rest of the engine. **S0 finalizes the G-buffer `ImageUsage` to `STORAGE`** (+ `COLOR` only for the mesh-raster attachments); the earlier "reserve both usage bits" hedge is unnecessary now that this is decided.

**Kickoff verification obligations (measurements, not choices):**
- **OQ-4 — `MAX_CONTACT_POINTS` 3D value + `Manifold` size.** Box2D-v3's 2 was 2D; 3D convex-convex needs up to 4 (box-box face contact). With a `Vec3` normal + `Vec3` anchors + 4 `ContactPoint`s + `u32` `BodyIndex` keys, the `<= 128` (2-cache-line) assert must be **verified by computing the actual `size_of` at kickoff**. Do NOT trust the live `manifold.rs:84-86` headroom comment — it was written for the 2D `ContactPoint` widened only in COUNT, not for `Vec3` anchors (O2). If it spills past 128, update the assert honestly (a 2-CL contact record is acceptable) — do not force-fit.
- **OQ-6 — windowing + Vulkan 1.3 dynamic-rendering posture (confirm at kickoff).** CLOSED: raw Win32 window (`window.rs`, Slice-1, HAVE) is the basic-slice windowing (zero-third-party); raw XCB/Wayland is a later Linux addition; CI render tests are headless-offscreen. Dynamic-rendering is CLOSED to `renderPass = VK_NULL_HANDLE` (no `VkRenderPass` object path). The basic slice **asserts the `dynamicRendering` 1.3 feature at device creation and fails fast** if absent (no `VkRenderPass` fallback is built for the basic slice — that is a deferred RHI seam). Target minimum = the dev Windows machine; confirm it exposes `dynamicRendering` at kickoff.

### 3.9 (referenced from OQ-1/OQ-2, CLOSED) — Transform3D ownership + physics/render unification

**Decision (resolving the former OQ-1 + OQ-2 as a pair, before P1/S1, W3).** A shared `Transform3D` POD lives in a **`boyko_scene` leaf crate** consumed by both pillars; physics keeps its lean hot `RigidBody { position, orientation }` column (PHYSICS-FOUNDATION D5 hot/cold — the integrate loop is NOT polluted with a 4×4 matrix), and a **`physics_to_transform` sync system — owned by `boyko_app`/demo glue, NEVER by either pillar crate** — derives the render `Transform3D` from the physics body each frame. **Why closed as a pair:** P1 already defines `RigidBody.position: Vec3, orientation: Quat`, so the transform decision is forced at P1, earlier than a deferred OQ-2 admitted; leaving it open risks P1 landing a physics-local transform and S1 a render-local one with an unscoped sync system. The `boyko_scene` leaf is the consistent answer to the same leaf-crate pattern used for `boyko_sdf_math` (§3.6) and preserves the dependency graph's no-render↔physics-coupling invariant: both depend on the leaf, neither on the other; the sync system lives in demo glue. **Trade-off:** one more leaf crate + one sync system per frame — accepted; it keeps the hot physics column lean and the crate graph acyclic.
