## Findings

- On the owner's windows-gnu toolchain, `thread_local!` goes through std's os-key path. That path allocates one `Value<T>` per thread per key through `System.alloc` (os.rs AlignedSystemBox::new), which bypasses any `#[global_allocator]`, so the design's deny gate cannot see it. This was read in the installed std source (library/std/src/sys/thread_local/guard/windows.rs:116), not measured. It applies to every `thread_local!` in the workspace. This group rows two of them (hooks/scope.rs:31, observers/propagate.rs:30) as class T.
- Three facts are each stored more than once. `ComponentPoolBundle.sparse_indexes` duplicates the Archetype's inline columns, whose `_reserved: u32` is unused. DenseStore liveness is encoded three ways: the s2e tombstone, the live bit, and free-list membership. `Archetype.component_ids` can be derived from a full-membership ComponentMask.
- A runtime-id query already exists: QueryState::with_component_ids at query_state.rs:128. The query_entities family therefore needs no new kernel feature.
- Stale comment: deep.rs:85 says the stack `Vec` stays in "inline capacity", but a Vec has no inline storage. `Vec::with_capacity(DEEP_WORKLIST_INLINE)` at :88 allocates on every call.
