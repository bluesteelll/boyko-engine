# Architecture review: Phase 11 — EntityCommands chaining + despawn

## Verdict
[ ] APPROVED
[X] CHANGES REQUESTED — 5 criticals + 5 warnings + 4 optionals

## Remarks

### Critical (blockers)

#### C1. `EntityCommands<'a>` field type `&'a mut Commands<'a>` is unsound and likely will not compile in idiomatic use
**Where**: §5.1 (lines 279-282), §5.2 (lines 296-298), §11.7 (lines 1408-1416), and every method using reborrow (§5.3).
**Problem**: The field is typed `commands: &'a mut Commands<'a>` — same lifetime `'a` on both the outer borrow and the inner generic parameter. That collapses the inner `Commands<'s>` generic to the outer borrow lifetime, which (a) makes the type invariant in `'a` (both positions of `'a` make `EntityCommands` invariant), and (b) forces `Commands` to outlive its own borrow — a classic self-referential pattern that the borrow checker rejects whenever the caller has any other live reborrow chain. `Commands::spawn(&mut self, ...) -> EntityCommands<'_>` will not be able to satisfy `EntityCommands<'a> { commands: &'a mut Commands<'a> }` because `&'a mut Commands<'s>` for `'a: 's` cannot be coerced to `&'a mut Commands<'a>` (lifetime shortening through `&mut` is illegal — `&mut` is invariant). Reborrow in `EntityCommands::reborrow` similarly fails because the field stores the wrong shape. The decision matrix Q2 (line 122) explicitly chose "single `'a`", but the field still has TWO lifetime positions tied to that same `'a`.
**Why critical**: blocks the entire Wave C — the file `entity_commands.rs` will not compile. This is the core data structure of the phase.
**What is needed**: redesign the field as `commands: &'a mut Commands<'s>` with two named lifetimes on `EntityCommands<'s, 'a>` (Bevy's actual shape, modulo Bevy's extra `'w`), OR collapse to a single named lifetime by storing `&'a mut CommandQueue` directly + a `PhantomData<&'a mut EntityMaster>` if EM access is still needed. Either way the architect must produce a 5-line code-sketch that compiles end-to-end with `let ec = commands.spawn(b); let id = ec.id();` AND `let mut ec = commands.spawn(b); ec.insert(c).insert(d);`. The current §12.1 type signature line `pub struct EntityCommands<'a> { entity: Entity, commands: &'a mut Commands<'a> }` does not survive `cargo check`.

#### C2. `Commands::spawn` body holds `&self.queue` and `&self.entity_master` simultaneously through `&mut self` — borrow conflict
**Where**: §5.5 (lines 425-431), `Commands` struct definition (lines 440-448).
**Problem**: the proposed body is:
```rust
let entity = self.world_ref.entity_master().reserve_entity(); // immutable borrow of `self`
self.queue.push(SpawnAtCommand { entity, bundle });            // mutable borrow of `self`
```
This is fine on the surface BUT the field structure `Commands<'s> { queue: &'s mut CommandQueue, entity_master: &'s EntityMaster }` carries TWO references with the SAME lifetime `'s`. When `Commands::spawn` takes `&mut self`, the borrow checker sees both fields, splits the field borrows, and that works — UNTIL the next call: `EntityCommands { entity, commands: self }` returns a borrow of `self` for `'_` that the caller will then chain `.insert(b)` on, which requires `&mut self.queue` AND keeps `self.entity_master` reachable. The chain `.insert(b)` inside `EntityCommands` does NOT access `entity_master`, but it does hold `&'a mut Commands` whose `entity_master` field exists. This is fine UNLESS Phase 11 ever wants `EntityCommands::reborrow` to call `commands.spawn()` recursively (it doesn't in v1 — OK) AND unless `Commands<'s>` is itself constructed via `unsafe impl SystemParam`. Look at §5.5's `get_param` snippet (lines 460-482): both `state: &'s mut CommandQueue` and `world.entity_master_shared()` (returning `&'s EntityMaster`) need to live for the **same** `'s`. But `state` comes from `SystemParam::State` storage owned by `SystemMeta`, while `entity_master_shared()` returns a lifetime tied to `UnsafeEcsCell<'w>`. The cell's `'w` is the system body's local scope, NOT `'s` (state scope). The proposed code lies about the lifetimes: `world.entity_master_shared()` cannot return `&'s EntityMaster` because the cell only carries `'w`. Concretely: `Self::Item<'w, 's> = Commands<'s>` forces the inner refs to use `'s`, but the EntityMaster borrow is bounded by `'w` (the cell's lifetime). Bevy gets around this with a 2-lifetime `Commands<'w, 's>`.
**Why critical**: Q2's "single `'a`" decision was applied to `EntityCommands` (defensible) and **also** to `Commands<'s>` (NOT defensible after adding EntityMaster). The plan claims §1.4 / §3 Q2: "boyko's `Commands` carries only the queue borrow"; §5.5 then adds a second borrow but does not lift the lifetime. Mathematically: cannot make a single-lifetime struct carry two borrows with different originating scopes.
**What is needed**: either (a) lift `Commands<'s>` to `Commands<'w, 's>` and propagate through the whole Phase 8d/8.5 surface — substantial migration; or (b) keep `Commands<'s>` single-lifetime by stashing a `*const EntityMaster` raw pointer in `Commands` (with `PhantomData<&'s EntityMaster>` for variance) — explicit unsafe, but no API surface explosion. The plan must pick one and walk through the lifetimes in `get_param`, including how `UnsafeEcsCell::entity_master_shared` is signed; today nothing in `UnsafeEcsCell` returns `&'s` — only `&'w`. Show the proposed signature of `entity_master_shared` and prove it composes.

#### C3. `apply_replace_in_place` calls `pool.drop_at` then `copy_nonoverlapping` — but immediately before that calls `world.get_component_raw_mut(entity, id)` which itself returns a `*mut u8` already; the proposed double-borrow path is incoherent
**Where**: §7.4 lines 1093-1119.
**Problem**: the snippet first `world.get_component_raw_mut(...)` returns `Option<*mut u8>`, then immediately on the next two lines re-derives `inland`, `archetype`, `pool` from `world` — but `world` is borrowed by the `if let Some(ptr) = ...` for the duration of the block. The line `let inland = world.entity_master.entities_inland[entity.id().0]` re-borrows `world` shared while `ptr` (a `*mut u8` derived from `get_component_raw_mut`) is still in scope. Raw pointers don't track aliasing, so this would compile, BUT the SAFETY contract on `pool.drop_at(unit_idx)` followed by `copy_nonoverlapping(bytes.as_ptr(), ptr, bytes.len())` requires that `ptr` and `pool`'s internal storage refer to the SAME byte range. The plan does not assert this — it derives them via two independent lookups. If `get_component_raw_mut` and `get_pool_mut(id)` resolve to different pool versions (e.g., after the pool grew between the two calls — impossible here because no mutation happens between them, but still: this needs to be stated). Worse: Phase 10 tick write `pool.write_changed_tick(unit_idx, current_tick)` — there is no such method exposed today (Grep confirms `write_changed_tick` exists at line 429 of `archetype.rs`, but it is `unsafe` and `pub(crate)` on `ComponentPool`); the snippet does not state it is unsafe.
**Why critical**: replace-in-place is the fast-path for the common case `commands.entity(e).insert(SameBundle)`. If its lifetime/aliasing story isn't airtight, every `.insert()` invocation that hits this path is UB or panicking.
**What is needed**: rewrite the `apply_replace_in_place` body as a single linear sequence: resolve `inland` first → mint `*mut Archetype` from inland → reborrow `&mut Archetype` → iterate bundle bytes → for each, `pool = archetype.component_pools.get_pool_mut(id)`, `pool.drop_at(row)`, `pool.write_at(row, bytes)`, `pool.write_changed_tick(row, current_tick)`. Drop the misleading detour through `get_component_raw_mut`. Add a SAFETY block enumerating: drop runs exactly once; the row is initialized before the next reader; ticks are written under `&mut Archetype`.

#### C4. `EntityMaster::reserve_entity(&self)` minting `Entity { id, generation: 0 }` collides with recycled IDs whose slot has non-zero generation
**Where**: §4.2 lines 204-211, EM1/EM2/EM4 (lines 109-113).
**Problem**: EM2 says "reserve_entity returns ONLY fresh IDs — never pops from `free_entity_ids`". Fine. But the atomic counter `next_entity_id` is shared with `allocate_entity(&mut self)`, which DOES pop from the free list when available. Sequence:
1. Worker calls `reserve_entity(&self)` → `fetch_add` returns id=42, mints `Entity::new(EntityId(42), 0)`.
2. Concurrently (well, with apply-window barrier they're not concurrent, but across frames) dispatcher's `allocate_entity` recycles id=42 from the free list — recycled IDs read `current_gen` from `entities_inland[42].generation()` (line 93 of `entity_master.rs`), which after one dealloc cycle is `1`, not `0`.
3. Worker's reserved `Entity(42, gen=0)` then enqueues `SpawnAtCommand`, which at apply time tries `create_entity_at(entity={42, 0}, ...)` while the slot's generation says `1`.
4. `is_entity_valid` at any read returns false because the stored generation is `1` and the handle's is `0`. The entity is silently dead.
The deeper issue: EM4 claims "any ID returned by `reserve_entity(&self)` is **strictly larger** than the max ID currently in `free_entity_ids`". This claim is FALSE if `allocate_entity(&mut self)` ever incremented `next_entity_id` (because it pulled from the counter, not from free-list, on an earlier frame), and a later `deallocate_entity` pushed that id back to free-list — now free_list contains an id < `next_entity_id.load()`. Then `reserve_entity` increments past that id, returning a fresh id that is INDEED `> max(free_list)`. So far so good. But the slot at `entities_inland[fresh_id]` has NEVER been touched (the slot index ≥ Vec.len() at construction unless `with_capacity` pre-resized to MAX). When dispatcher later calls `register_entity_with_ptr(Entity(fresh_id, 0), ptr, idx)`, the debug_assert at line 134-137 of `entity_master.rs` fires:
```rust
debug_assert!(
    sparse_idx >= self.sparse_to_active.len()
        || self.sparse_to_active[sparse_idx] == u32::MAX,
    "Entity already present in Phase 7 fast store"
);
```
This won't fire (the slot is empty), but the SAFETY assumption that the slot's generation was previously bumped via dealloc-then-recycle doesn't hold for a fresh path. So the generation-stamp in `EntityInland::new(ptr, idx, entity.generation())` overwrites whatever was there with `0`. OK so far. BUT: what if `entities_inland.len()` < `fresh_id`? `create_entity_at` (§6.2 lines 647-652) resizes — fine, but the new slots are `NULL` with `generation=0` (per `EntityInland::NULL`), and the entity's generation is also `0`. Match. So this specific sequence works.

The REAL race: worker A calls `reserve_entity` → id=42, gen=0. Worker B (same frame, parallel) calls `commands.entity(stale_handle_for_42)` where the stale handle has gen=0 (some legacy). Both code paths produce identical `Entity(42, 0)` handles, except worker A's becomes valid at apply, while worker B's was always stale. There's no way to distinguish them. Bevy uses a dedicated "reserved" range with a sentinel to mark "exists but not yet flushed". The plan's "generation=0 always" makes the validity check ambiguous in the case where the user fabricates an Entity (which the plan permits via `Commands::entity(any)`).
**Why critical**: silent miscompile of `is_entity_valid` semantics. EC13 documents that "EntityCommands::id() returned Entity is invalid for query lookups until apply" — but the plan never says HOW `world.has_entity(returned_id)` reports false BEFORE apply. Today's `is_entity_valid` checks `!inland.is_null() && generation matches`; for a freshly-reserved-but-unregistered ID with `inland=NULL`, the check returns false (good). But after `register_entity_with_ptr`, the gen-0 stamp must match the user's handle — which it does only if the slot was never previously used. If the same id was reserved-then-leaked (§4.5 leak scenario), no one bumps the generation, and re-reservation of the same id would happen via... wait, atomic counter is monotonic, so no re-reservation. OK. But §4.5's reservation reaper (deferred to Phase 12) is what guarantees the leaked id never gets recycled; without it, the leak permanently consumes the slot. That's acceptable IF the plan documents that `next_entity_id` only ever grows. The architect must explicitly state: "reserve_entity never produces an id that was previously emitted by allocate_entity; recycled IDs go via allocate_entity's free-list path only; the two minting paths share the counter but never the free list." Today's plan (§4.5) says workers "could leak" but does not prove non-collision in the steady state.
**What is needed**: a concrete proof-by-cases for the four interleavings: (worker reserve, dispatcher fresh allocate), (worker reserve, dispatcher recycled allocate), (worker reserve, dispatcher reserve via reserve_entity called from dispatcher thread itself), (back-to-back worker reserves). Each case must terminate with "the resulting `Entity(id, gen)` is unique across all live and reserved IDs at the relevant tick boundary." The proof must address how a stale-handle-fabricated `Entity(42, 0)` passed to `commands.entity(42)` is distinguished from a reserved-not-yet-applied `Entity(42, 0)`. (Likely answer: it isn't — both are "valid-looking handles" and the apply-time `is_entity_valid` check resolves it. But this must be stated.)

#### C5. Drop semantics in `migrate_entity_insert` for "retained" components: source pool keeps a "live" byte range that target pool now also references — double-ownership window without explicit forget discipline
**Where**: §7.2 lines 900-980, especially the comment block at line 986 ("Wait — there's a drop ordering subtlety...").
**Problem**: the architect spotted the issue and proposes `forget_entity` + `swap_remove_unit_no_drop` (§7.2 lines 988-1005). Good. But the proposed sequence is:
1. Collect `retained_slots[]` — `&[u8]` borrows into source's pool memory.
2. Call `target.create_entity(retained_slots + bundle_slots)` — target memcpys FROM the borrows.
3. Call `source.forget_entity(source_row)` — swap-remove without drop.

Between steps 2 and 3, **target's pool owns the bytes** AND **source's pool still has the bytes addressable** (no `forget_entity` yet). If `target.create_entity` triggers a pool grow (`Chunk` reallocation), it may move pool memory — but Phase 8.5 SBC2 says chunks are append-only with stable addresses. OK. The real concern: `target.create_entity` accepts `&[(ComponentId, &[u8])]` — those slices borrow from `source`. The function may iterate them multiple times (debug_assert, then push). If during the iteration `target` grows AND that grow goes through the arena which is the SAME arena as `source`'s pools (`EcsMaster::arena`), the arena's bump-alloc may move... actually no, the arena never moves existing allocations (it only appends new chunks). Confirmed safe.

The DROP issue the architect identified is correct, and `forget_entity` is the right fix. But the FIX itself has a gap: `forget_entity` is described as "same logic as `remove_entity` but skips per-component Drop". Look at today's `Archetype::remove_entity` (lines 479-510 of `archetype.rs`): on `RemoveOutcome::Last` it calls `self.component_pools.pop_entity()` which internally calls each pool's drop_fn. On `Swapped`, it swap-removes the row and drop_fn's the original. `forget_entity` must skip drop_fn in BOTH branches. The plan only mentions "swap_remove_unit_no_drop / pop_entity_no_drop" — fine in name, but the source pool's per-row tick storage ALSO needs to swap-remove (not drop, ticks are POD); the plan does not mention tick rows in `forget_entity`.

Worse: in §7.3 `migrate_entity_remove` lines 1057-1062, `drop_at(source_row)` runs **before** `forget_entity(source_row)`. But `forget_entity` then swap-removes — meaning the last row's bytes get swapped INTO `source_row`. If we already dropped `source_row`'s component C, fine, that slot is logically uninitialized. But the swap copies bytes from `last_row` to `source_row` — for the C pool, this writes new live bytes over the freshly-dropped slot. After the swap, `last_row` is logically uninitialized in the C pool. `forget_entity` then pops the C pool's tail to shrink the column — but if "forget" means "do not drop", the popped tail's logical state (which contains valid bytes for the entity that was at `last_row` BEFORE the swap... wait, that entity got moved INTO `source_row`. Now the C-pool's last_row contains... the SAME bytes as the new source_row, post-swap. The forget path then "pops without drop" — leaks the bytes that the swap left at last_row.

Concretely: in a remove migration for entity E removing component C from archetype {A,B,C}:
- E's row is `source_row=5`, last entity at `last_row=10`.
- `drop_at(C, 5)` — drops C@5.
- `forget_entity(5)` — swap A@10 into A@5, swap B@10 into B@5, swap C@10 into C@5 (overwriting the now-dropped C@5 with C@10's bytes), then pop A@10, B@10, C@10 without drop.
- C@10 has now been MOVED (via swap_remove) to C@5 and the pop says "do not drop the tail" — but C@10's bytes were copied to C@5 (live for the moved entity), and the tail is "logically gone". Correct.
- The moved entity at row 10 (let's call it M) needs its `EntityInland.unit_index` updated to 5. `RemoveOutcome::Swapped { moved_entity }` returns M's id — the plan handles this at line 1069.

OK so the actual swap-semantics work out... but only if `forget_entity` is **specifically** "for retained components: full swap-remove behaviour; for non-retained components in the remove case: skip drop because already dropped by the caller". The plan does not differentiate. As written, `forget_entity` would also "skip drop" for the C column at `last_row` after the swap-pop, which is exactly what we want for retained (A, B) but redundant for the just-dropped C.

The bigger issue is for **insert migration**: at §7.2 line 962 the plan says "Bundle's bytes were consumed into target ... So source.remove_entity handles the swap-remove safely" — but it then asks for `forget_entity` instead. The retained components in source were memcpy'd into target. Source still owns the byte range. `forget_entity` swap-removes without drop. The swap brings `last_row`'s bytes into `source_row`. For column A: source's A@source_row had its bytes copied (memcpy) into target's A@new_row. Now source A@last_row's bytes overwrite source A@source_row — meaning the bytes that target has are NOT the bytes source has at source_row anymore. But target memcpy'd already, so target's copy is independent. OK, the memcpy created an independent copy and the swap just rearranges source. The forget-pop at the end drops the last row WITHOUT calling drop — but A@last_row's logical owner (the moved entity M) now lives at A@source_row, so the pop of A@last_row's slot is correct: those bytes were moved (via swap) to source_row, the tail slot is logically uninitialized. **No leak.**

So the algorithm is sound, but the plan's English is misleading and the SAFETY blocks the developer will need to write are absent.
**Why critical**: this is the entire migration story. If the developer reads §7.2 verbatim and writes `forget_entity` as "swap-remove without drop", they will reach a state where retained bytes that were memcpy'd into target are also still readable from source's now-deallocated slot — but `Drop` won't run twice (good). Where the algorithm breaks is in the **tick storage** rows: the plan never mentions whether `forget_entity` also swap-removes the tick rows. If it doesn't, then `source.entity_count` decreases but `pool.added_ticks[]` does not — the next read on `source` for an unrelated entity will see stale tick bytes at the swapped row.
**What is needed**: §7.2's description of `forget_entity` must be expanded into a formal contract: "for every pool in this archetype, perform `pool.swap_remove_index(idx)` which (a) copies last-row bytes into idx, (b) decrements pool.count, (c) does NOT invoke drop_fn on the source-row bytes (they were moved by the caller). For tick rows, perform the same swap (no drop, POD)." Then the implementation Step 9 must add `ComponentPool::swap_remove_index_no_drop` that handles both the byte storage AND the two tick storages atomically. The plan as written gives the developer a fork in the road they will likely take wrong.

### Warnings (must be resolved)

#### W1. §6.4 RemoveCommand idempotency claim — "If source does not have C, no-op" — does not match EC11 + Q4 stale-entity policy
**Where**: §6.4 lines 791-797.
**Problem**: the plan says `if !source_arch.component_ids().contains(&component_id) { return; }` — silent no-op, not even a `debug_assert!`. But Q4 says non-`try_*` variants `debug_assert + silent no-op`. For consistency, this branch should also `debug_assert!(false, "RemoveCommand for absent C")`. Currently inconsistent: stale-entity is debug-asserted (line 786), absent-component is silently no-op (line 796). One of the two policies must apply uniformly.
**Solution options**: (a) silent no-op for "absent C" — argue this is idempotent and expected (Bevy parity); (b) debug_assert for "absent C" — flag the user that they're issuing a redundant remove. The plan must pick and justify against Bevy's actual behaviour (which is silent no-op per Issue #10166 — option a). Document explicitly.

#### W2. Generation-bump on free-list pop interacts with `reserve_entity` returning `generation=0` only — recycling regression vs Phase 7
**Where**: §4.2 line 210 ("`Entity::new(EntityId(id), 0)`"), EM2 lines 110-111.
**Problem**: today's `allocate_entity` (line 84-107) returns recycled IDs with their **bumped** generation (line 94: `Entity::new(id, current_gen)`). Phase 11's `reserve_entity` ALWAYS returns generation 0 because it doesn't consult the free list. If the dispatcher and workers race for ID allocation across a frame boundary, recycled-id-via-allocate_entity and fresh-id-via-reserve_entity will mint different generations for what should be observationally-identical "newly minted entities". A library user writing `let e1 = commands.spawn(b1); let e2 = world.allocate_entity();` (mixed legacy + new path) gets two entities whose generation semantics differ: e1.gen=0 forever, e2.gen=N (recycled). This is acceptable IF the plan asserts that `reserve_entity` is the ONLY path workers ever use, and the legacy `allocate_entity` is dispatcher-only. The plan says so in EM2 but doesn't enforce — the `pub fn allocate_entity(&mut self)` signature remains pub.
**Solution options**: (a) deprecate-and-document: `allocate_entity` should be renamed to `allocate_entity_dispatcher_only` or moved to `pub(crate)` since `EcsMaster::create_entity` is the public path. (b) make `reserve_entity` ALSO consult the free list — requires it to be `&mut self` or to redesign the free list as lock-free (Path B, which Q1 explicitly rejected). The plan should pick (a) — confining `allocate_entity` and demanding the architect prove that no current public caller relies on the recycled-gen behaviour.

#### W3. §9.2 — `Archetype::create_entity_with_ticks` API surface is added BUT `SpawnAtCommand` still uses `create_entity` (line 633 of §6.2 shows `archetype.create_entity(...)` not `create_entity_with_ticks`)
**Where**: §6.2 lines 619-657 vs §9.2 lines 1257-1280.
**Problem**: The plan introduces `create_entity_with_ticks` specifically for retained-tick preservation during migration. But `SpawnAtCommand::apply` (§6.1) calls `archetype.create_entity(...)` (the existing path). Insert migration calls `create_entity_with_ticks`. Asymmetry: a freshly-spawned entity always has fresh ticks (correct via `create_entity`), but a migrated entity needs to preserve original ticks (correct via `create_entity_with_ticks`). Fine. But §10.2 line 1313 lists InsertCommand apply with "+ tick overhead (80 ns)" — that's specifically the 2 extra reads per retained component. The §6.1 `SpawnAtCommand` does NOT pay this cost. Good. The asymmetry is intentional. **However**, the plan does not address what happens when the SAME `create_entity_with_ticks` is called and `current_tick` argument is also passed — is `current_tick` used as a fallback for components that don't have explicit ticks in the slice? §9.2 says the slice is `&[(ComponentId, &[u8], Tick /* added */, Tick /* changed */)]` — every entry has its tick pair, so what role does the trailing `current_tick: Tick` argument play? Possibly only for tick-rollover-check infrastructure (Phase 10 CD5). Not clarified.
**Solution options**: clarify the role of `current_tick` parameter in `create_entity_with_ticks`. If it's purely metadata (e.g., for `last_check_tick`-style invariants), say so; if it's a fallback when a component is missing from the slice, that should be impossible by construction (the slice has every component).

#### W4. `merged_archetype_id` stack-path bail at >16 components silently degrades — but the bail is in a hot path that runs every InsertCommand::apply, not just the first
**Where**: §6.3 lines 749-759.
**Problem**: the plan says "If a future profile shows >16-component migrations as a hotspot, Phase 12's `Edges` cache eliminates this". But the plan ALSO says (line 752) `Vec::with_capacity(20)` heap-allocates on every cold-path call. For an apply-loop processing 1000 migrations on archetypes with 17 components, this is 1000 heap allocations PER FRAME. Even if rare, it violates principle #5 ("Minimum allocations in the hot path"). The right pre-Phase-12 fix is a thread-local scratch `Vec` reused across calls (since apply runs on the dispatcher, a single static reusable buffer suffices). Alternatively, raise the stack limit from 16 to 32 — wider stacks (1KB total) still fit in cache.
**Solution options**: (a) raise the stack limit to 32; (b) use a `RefCell<Vec<ComponentId>>` field on `EcsMaster` for the apply-time scratch — zero alloc after warmup. The plan must address this BEFORE merging because adding it post-hoc means changing every `migrate_entity_*` call site.

#### W5. `bench_reserve_entity_parallel_8_threads` target "≤ 100 ns/op under contention" is significantly higher than the §1.2 single-thread target "≤ 5 ns" — the plan does not analyze the contention curve
**Where**: §1.2 line 41, §13.4 line 1649, §11.8 line 1431-1433.
**Problem**: §11.8 acknowledges cache-line contention on `next_entity_id`. Single-thread bench targets 5 ns. Parallel bench targets 100 ns — 20x degradation. The plan accepts this without quantifying when 100 ns becomes a problem. At 10k spawns/frame × 100 ns = 1 ms — 20% of the 5 ms budget. Plus the §11.8 dispatcher-vs-worker false-sharing argument is correct in steady state, but the plan's claim "150 µs extra under heavy contention" (line 1432) doesn't match the bench target (100 ns × 10k = 1 ms). Math inconsistency.
**Solution options**: reconcile the numbers. Either the bench target is wrong (should be ≤ 30 ns to fit the §10.3 budget) or the §10.3 budget needs to bake in the parallel atomic-contention cost. Likely the right move: add a §10.5 "parallel contention sensitivity" subsection that says: for N workers, expect K ns/op linear in N up to some saturation point; cite a real measurement from a sample bench.
